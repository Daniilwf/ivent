# Игровой ивент — инструкции для агента

Сайт для дружеского сезонного соревнования по прохождению игр. Полная спецификация — `docs/SPEC.md`, это источник истины. Перед каждой задачей перечитывай нужные разделы. Разделы «Уточнения правил после перепроверки» и «Трудности реализации» обязательны.

## Стек

Не меняй без явного согласования:

- .NET 10 (LTS), ASP.NET Core, EF Core, SQLite в режиме WAL.
- SignalR для обновлений в реальном времени.
- React + TypeScript + Vite. Карта игрока — SVG с зумом и перетаскиванием. Редактор карты — `@xyflow/react` (этап 2).
- Логи: Serilog в файл с ротацией. Контракт API: OpenAPI из бэкенда, TypeScript-клиент фронтенда генерируется из него (openapi-typescript).
- Интерфейс: Tailwind CSS с темой из своих токенов, примитивы Radix UI (стартовые компоненты можно взять из shadcn/ui), иконки lucide, анимации — Motion (бывший Framer Motion). Шрифты хранятся на своём сервере.
- Тесты: xUnit и FsCheck для .NET, Stryker.NET для мутационного тестирования движка, Vitest и Testing Library для фронтенда, Playwright для E2E и исследовательского тестирования. Покрытие — coverlet.
- Docker (многостадийная сборка), docker compose, Caddy для HTTPS. Образы собираются в GitHub Actions.
- Разработчик на Windows: всё запускается через `dotnet`, `npm` и `docker compose` без WSL-специфики. В `.gitattributes` — LF для `*.sh`.

- Строгость .NET: Nullable, TreatWarningsAsErrors, `.editorconfig`, центральное управление версиями пакетов (`Directory.Packages.props`), Microsoft.CodeAnalysis.BannedApiAnalyzers (в движке запрещены `DateTime.Now`, `DateTime.UtcNow`, `Random`, `Guid.NewGuid` без абстракции), архитектурные тесты на NetArchTest.
- Строгость фронтенда: TypeScript strict, ESLint, Prettier.
- Git: husky и lint-staged перед коммитом, gitleaks против утечки секретов, коммиты в формате Conventional Commits (`feat:`, `fix:`, `chore:`), Dependabot раз в месяц с группировкой обновлений.

Не добавляй: Postgres, Redis, брокеры сообщений, микросервисы, внешние провайдеры входа, уведомления в Discord или Telegram.

  GameEvent.Web.Tests        — интеграционные тесты API

/data/import                 — исходные файлы для импорта (не в git, кроме .gitkeep)

Код внутри проектов раскладывается по механикам (`Rolls`, `Runs`, `Map`, `Economy`…), а не по техническим слоям. Одна механика — одна папка с командами, событиями, обработчиками и тестами рядом.

## Архитектурные инварианты

Нарушать нельзя. Если задача требует нарушения — остановись и спроси.

1. **Движок — чистая библиотека.** Время только через `IClock`, случайность только через `IRandomSource`. Никаких `DateTime.Now` и `new Random()` в движке. Это проверяют анализатор запрещённых API и архитектурные тесты, а не только ревью.
2. **Все изменения состояния — команды**, которые выполняются по одной через единую очередь (`System.Threading.Channels`) с одним потребителем. Админские правки и таймеры идут через ту же очередь. Записей в БД мимо очереди нет.
3. **Одна команда — одна транзакция**: события в лог (`GameEvent` с `CommandId`) плюс обновление состояния.
4. **События хранят результаты** (выпавшие кубики, выбранную игру, промахи колеса), а не намерения. Повтор по логу детерминирован.
5. **Все игровые числа — в `Ruleset`** (JSON-конфиг сезона, по умолчанию `docs/ruleset.default.json`). Балансных констант в коде нет. Прохождение хранит снапшот нужных правил в момент ролла.
6. **Броски и выбор из колёс — только на сервере.** Клиент анимирует готовый результат.
7. **Эффекты описываются данными**: триггер, условие, селектор целей, список базовых действий. Новое базовое действие — один класс-обработчик с JSON-схемой параметров. Базовых действий не больше 12, новые — только под конкретную потребность.
8. **Лимит цепочки эффектов**: 3 уровня вложенности и 50 событий на команду, дальше обрыв с записью в лог.
9. **Очки и монетки — колонки**, прочие ресурсы — словарь в JSON. По JSON-полям не фильтруем и не сортируем.
10. **Карта в движке — граф с первого дня.** Линейная карта этапа 1 — это цепочка клеток, сгенерированная из конфига.
11. **Мягкое удаление** для пользователей, игр и определений объектов.
12. **Откат — команда целиком** через компенсирующие события, в обратном порядке. Если от отменяемой команды зависят более поздние, откат отказывает и показывает их.
13. **Интерфейс на русском**, все тексты интерфейса в одном словаре. Код, идентификаторы, комментарии и коммиты — на английском.

## Ловушки предметной области

Самые частые места, где правила легко реализовать неправильно. Подробности в `docs/SPEC.md`.

- Очки и позиция — разные показатели. Кубы за прохождение меняют оба, клетки-телепорты — только позицию, броски предметов для перемещения очков не дают.
- Первое место — первый дошедший до финиша, остальные места — по очкам. Первый финиш предварительный до одобрения пруфа.
- После финиша первым игрок заморожен: очки не растут, на других не влияет, по нему не бьют. Финишировавшие позже получают бонус один раз, их позиция фиксирована, очки продолжают расти.
- Дроп отнимает и очки, и позицию, но не ниже чекпоинта и старта.
- Игра занята, пока её кто-то играет. Пройденная в сезоне — недоступна всем. Дропнутая другим — доступна. Своя дропнутая или техдропнутая — исключена для тебя.
- Колесо категорий крутится только по категориям, где есть доступные игры. Промахи фиксируются в логе, бесконечных рероллов нет.
- Кубики за прохождение хранятся по отдельности: при правке часов после броска недостающие докидываются, лишние снимаются с конца.
- Эффекты от других применяются только к будущим шагам цели.
- Клетки срабатывают при любой остановке, включая чужой толчок, кроме клетки назначения телепорта.
- Движение назад идёт по пройденным рёбрам (отрезками), при нехватке истории — по основному входящему ребру.
- После дедлайна броски запрещены, пруфы принимаются. Итоги — только после проверки всех пруфов.

## Начало и конец сессии

`docs/PROGRESS.md` и `docs/DECISIONS.md` — твоя память между запусками.

- **В начале каждой сессии** прочитай `PROGRESS.md` (этап, что сделано, где остановился, следующий шаг), `DECISIONS.md` и открытые пункты `BUGS.md`. Убедись, что сборка и тесты зелёные, прежде чем менять код.
- **Во время работы** дроби большие задачи на шаги, которые можно закончить за одну сессию. Перед рискованной правкой — коммит.
- **Если контекст подходит к концу**, сначала обнови `PROGRESS.md`, потом продолжай.
- **В конце сессии** обнови `PROGRESS.md` (сделано, где остановился, следующий шаг, известные проблемы) и `DECISIONS.md`, закоммить. Следующая сессия должна продолжить без пересказа.

## Термины, конфиг и контент

- **`docs/GLOSSARY.md`** — единственный источник названий. В интерфейсе — русский термин из глоссария, в коде — английское имя оттуда же. Новый термин сначала добавляется в глоссарий.
- **`docs/ruleset.default.json`** — конфиг по умолчанию, **`docs/RULESET.md`** — описание полей. JSON-схема генерируется из C#-типов конфига, тест проверяет, что конфиг по умолчанию её проходит. Числа в нём временные.
- **`docs/CONTENT.md`** — формат предметов, эффектов, ивентов, достижений, зон, клеток, голосований и челленджей. Каждый пример оттуда — приёмочный тест движка на своём этапе. Если формат приходится менять, обнови примеры и запиши причину в `DECISIONS.md`. Уже на этапе 1 не принимай решений, которые сделают этот формат невозможным.

## Эксплуатация

- **Обновления посреди сезона ничего не ломают**: перед деплоем автоматический бэкап, миграции проверяются тестом на копии демо-базы предыдущей версии, у миграции есть откат или план восстановления.
- **Новые механики** выкатываются выключенными флагами в `Ruleset.Features`. Выключенная механика не видна в интерфейсе и отклоняется движком. Поэтому `main` всегда можно выложить, даже если механика не закончена.
- **CI/CD** — по разделу «CI/CD» в `docs/SPEC.md`. Workflows: `ci.yml` (каждый push и PR), `nightly.yml` (только если были коммиты), `deploy-staging.yml` (автоматически после зелёного `main`), `deploy-prod.yml` (только ручной запуск и только версия, прошедшая тестовую копию). Образ собирается один раз и передаётся на сервер по SSH (`docker save | ssh … docker load`); реестр образов не используется.
- **Экономь минуты GitHub Actions**: кэш NuGet и npm, отмена параллельных прогонов одной ветки, фильтры путей, ночные прогоны только при изменениях, Stryker раз в неделю. Держи учёт среднего времени прогонов в `docs/RUNBOOK.md`.
- **Сервер**: российский VPS на 1 ядро и 1 ГБ памяти, до 300 ₽ в месяц. Бюджет памяти боевого процесса — до 400 МБ под нагрузкой демо-сезона: .NET в режиме экономии памяти (Workstation GC, `DOTNET_GCConserveMemory`), лимиты памяти контейнеров, файл подкачки 1–2 ГБ, тестовая копия запускается только на время проверки и останавливается после. Потребление памяти проверяется в `/release` и описано в `docs/RUNBOOK.md`.
- **Миграции во время сезона только расширяющие**: добавлять можно, удалять и переименовывать — только между сезонами. Миграции запускаются отдельным шагом перед стартом приложения, а не при старте.
- **Дымовые тесты** — отдельный набор Playwright с тегом `@smoke`, который работает против любого адреса. На боевом сайте — только чтение.
- **События в логе не переписываются.** Если меняется формат события, у него появляется версия и преобразование при чтении.
- **Наблюдаемость**: Serilog в файл с ротацией, страница «Ошибки» в админке (последние исключения с запросом и пользователем), `/health`.
- **Контракт API**: API-типы на фронтенде руками не пишутся, только генерируются из OpenAPI. CI падает, если сгенерированный клиент устарел.
- **`docs/RUNBOOK.md` ведёшь ты**: развернуть с нуля, обновить, откатить, восстановить из бэкапа, начать и закрыть сезон, добавить игрока посреди сезона, сбросить пароль, что делать при падении сервера. Каждый пункт проверен руками хотя бы раз.
- **Демо-сезон** в сиде: 16 игроков, весь пул, сотни событий во всех состояниях. На нём проверяются дизайн, скорость и миграции.

## Тесты

Подробная стратегия — `docs/TESTING.md`. Главное:

- **Всё покрыто тестами**: движок — сценарные тесты и инварианты на случайных партиях, API — интеграционные тесты, фронтенд — Vitest, сквозные сценарии — Playwright.
- **`docs/TEST_MATRIX.md`** связывает каждое правило спецификации и каждую строку «Проверки на дыры» с тестами. Правило без теста — незакрытая задача.
- **Каждый эндпоинт** имеет тесты на успех, на запрет чужой роли или чужому игроку и на невалидный ввод.
- **Баг сначала воспроизводится падающим тестом**, потом исправляется.
- **Тест нельзя удалить, пропустить или ослабить, чтобы он прошёл.** Если тест неверен, опиши причину в `docs/DECISIONS.md` и дождись согласования.
- **В конце каждого этапа** — сессия исследовательского тестирования: агент ходит по сайту в браузере как новичок, хитрый игрок, админ и игрок с телефона, пытается сломать, записывает находки в `docs/BUGS.md` и закрывает их тестами.
- **Тестовые эндпоинты** (перемотка времени, сценарии, зерно случайности) существуют только в Development, Test и на тестовой копии (Staging), только для админа; на боевом сайте их нет (D-220).

## Дизайн

Подробные правила — `docs/DESIGN.md`. Заказчик не дизайнер: за то, чтобы сайт выглядел хорошо и был удобен, отвечаешь ты. Главное:

- **До кода интерфейса** — 3 направления дизайна с превью главного экрана на реальных данных и скриншотами. Дождись выбора.
- **Дизайн-система**: все цвета, шрифты, отступы, скругления и анимации — токены в одном месте, страница `/styleguide` со всеми компонентами и состояниями. Значения вне токенов запрещены линтером.
- **Сначала телефон 390 px**, потом десктоп. Одно главное действие на экран.
- **Все состояния**: загрузка, пусто, ошибка, успех; у кнопок — наведение, фокус, нажатие, отключено, загрузка.
- **Доступность уровня WCAG AA**: контраст, видимый фокус, работа с клавиатуры.
- **Зрелищность только в главных моментах**: колесо, кубы, движение фишки, финиш. Остальное спокойно.
- **Избегай шаблонного вида** из раздела «Чего избегать» в `docs/DESIGN.md`.
- **Каждый новый экран** снимается скриншотами на 390×844 и 1440×900 и проверяется по чек-листу, находки — в `docs/DESIGN_REVIEW.md`.

## Как работать

- Работай по этапам из раздела «Этапы разработки» в `docs/SPEC.md`. Следующий этап не начинай без подтверждения.
- **Сначала тонкий сквозной срез.** В каждом этапе сначала сделай минимальный путь новой механики от базы данных до экрана, работающий целиком, и только потом расширяй. Архитектурные ошибки должны всплывать в первый день, а не через неделю.
- В начале этапа составь план в `docs/PROGRESS.md`: задачи по порядку, у каждой критерий готовности. Дождись подтверждения, потом выполняй по одной и отмечай готовое.
- Движок пиши через тесты. Формат: «дано состояние → команды → ожидаемые события и состояние».
- Если в спецификации нет ответа, выбери самый простой вариант, совместимый с ней, по возможности вынеси его в `Ruleset` и запиши в `docs/DECISIONS.md` (дата, вопрос, решение, почему). По мелочам не останавливайся.
- Останавливайся и спрашивай только о решениях, которые трудно отменить: схема данных, публичный контракт движка, безопасность, противоречия в спецификации.
- Открытые вопросы из спецификации реализуй с указанными там дефолтами через конфиг.
- **`docs/SPEC.md` меняется только через `/spec-update`** после моего явного подтверждения. Сам предлагай изменения в `docs/DECISIONS.md` с пометкой «нужно решение». Никогда не меняй спецификацию, чтобы она совпала с кодом: если код расходится со спецификацией, чинится код или ты спрашиваешь меня.
- **`main` всегда рабочий.** Работа идёт в ветках на задачу или срез (`feat/…`, `fix/…`). Слияние в `main` — после `/review` и зелёного CI, с моего подтверждения.
- Маленькие коммиты в формате Conventional Commits. Перед коммитом: сборка, линтер, все быстрые тесты.
- Секреты не коммить. Конфиг через переменные окружения, пример в `.env.example`.
- Контент (игры, категории, позже предметы и ивенты) загружается через сид или импорт JSON, а не зашивается в код.

## Команды проекта

Все команды — скрипты корневого `package.json`. Агент, хуки, CI и человек вызывают одно и то же. Создай их в первой же задаче этапа 1, даже если сначала часть из них пустые заглушки. Хуки Claude Code опираются на `format:file`, `check:stop` и `test:fast`.

| Команда | Что делает |
| --- | --- |
| `npm run format:file -- <путь>` | форматирует и линтит один файл: `dotnet format` для .cs, Prettier и ESLint для фронтенда |
| `npm run check:stop` | быстрая проверка перед концом хода: сборка, линтеры, архитектурные тесты, быстрые тесты затронутых частей; укладывается в 3 минуты |
| `npm run test:fast` | все быстрые тесты .NET и фронтенда |
| `npm test` | все тесты, кроме E2E и длинных |
| `npm run test:e2e` | Playwright |
| `npm run test:smoke -- <адрес>` | дымовые тесты против тестовой копии или боевого сайта |
| `npm run test:invariants:long` | длинный прогон случайных партий |
| `npm run test:mutation` | Stryker по движку |
| `npm run coverage` | отчёт о покрытии |
| `npm run dev` | бэкенд и фронтенд с горячей перезагрузкой на маленьком сиде |
| `npm run dev:demo` | то же на демо-сезоне |
| `npm run seed:demo` | пересоздать демо-сезон |

## Инструменты агента

Папка `.claude/` уже настроена. Не меняй её без согласования.

- **Разрешения**: сборка, тесты, npm, docker compose и локальный git разрешены без вопросов. `git push`, слияния, теги, ssh и деплой спрашивают меня. `docs/SPEC.md` правится только через `/spec-update` с моим подтверждением, `.env` читать нельзя, разрушительные команды запрещены.
- **Хук после правки файла** вызывает `format:file`. Если он упал, исправь проблему сразу.
- **Хук в конце хода** вызывает `check:stop`, если изменился код. Пока проверка красная, закончить ход нельзя. Если ты посреди работы и тебе нужен мой ответ, создай `.claude/state/allow-stop-once` и в ответе прямо напиши, что красное и почему. Не используй это, чтобы уйти от исправления.
- **Хук на старте сессии** подкладывает сводку из `docs/PROGRESS.md`. Держи раздел «Сейчас» в этом файле актуальным.
- **Субагенты** в `.claude/agents/`:
    - `test-author` — пишет падающие тесты по спецификации до реализации, не глядя в код;
    - `rules-auditor` — сверяет поведение со спецификацией и матрицей тестов;
    - `code-reviewer` — ревью по инвариантам, глоссарию и качеству тестов;
    - `security-reviewer` — вход, права, файлы, ссылки, API, деплой;
    - `bug-hunter` — исследовательское тестирование в браузере;
    - `design-reviewer` — ревью интерфейса по `docs/DESIGN.md`.
- **Порядок работы над задачей с игровой логикой**: `test-author` → реализация → `rules-auditor` → `code-reviewer` (плюс `security-reviewer`, если задача его касается) → коммит. Новый экран — плюс `design-reviewer`.
- **Навыки** в `.claude/skills/`, их вызываю я: `/status`, `/next-phase`, `/review`, `/bughunt`, `/design-review`, `/release`, `/hotfix`, `/preseason`, `/session-end`, `/add-content`, `/import-bugs`, `/spec-update`.
