name: spec-update
description: Внести в docs/SPEC.md изменения, которые я явно утвердил. Только по моей команде.
disable-model-invocation: true
argument-hint: "<что поменять или номера решений D-N>"
---

Обновляем спецификацию: $ARGUMENTS

1. **Проверь, что изменение утверждено мной.** Это либо текст этой команды, либо решения D-N в `docs/DECISIONS.md`, где стоит моё решение. Если утверждения нет — остановись и спроси.
2. **Найди все места в `docs/SPEC.md`, которые затрагивает изменение**: основной раздел правила, «Уточнения правил», «Проверка на дыры», «Модель данных», «Этапы разработки», «Открытые вопросы». Правило должно быть описано в одном месте полностью, а в остальных — согласовано с ним, без противоречий.
3. **Пиши в стиле спецификации**: короткие предложения, термины только из `docs/GLOSSARY.md`, без объяснения, почему поменяли, — это в DECISIONS.md.
4. **Покажи мне `git diff docs/SPEC.md`** и список других документов, которые нужно поправить вслед: GLOSSARY, RULESET, `ruleset.default.json`, CONTENT, TESTING, TEST_MATRIX. Дождись моего подтверждения.
5. **После подтверждения:**
    - примени правки и обнови связанные документы;
    - в `docs/DECISIONS.md` у решения отметь «перенесено в SPEC» с датой;
    - в `docs/TEST_MATRIX.md` сошлись на новый текст спецификации;
    - если меняется поведение, добавь задачи в `docs/PROGRESS.md`: сначала тесты, потом код.
6. **Закоммить отдельно от кода**: `docs(spec): <кратко>`.

Никогда:
- не меняй спецификацию, чтобы она совпала с уже написанным кодом;
- не удаляй правила без моего явного решения;
- не смешивай в одном обновлении несвязанные изменения.
