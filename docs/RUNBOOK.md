## Закрыть сезон

Не проверено руками (появится в админке, этап E; пока — через API).

1. Дедлайн задаётся заранее: `POST /api/admin/seasons/{id}/deadline` с `{commandId, deadline}` (UTC или со смещением, хранится в UTC). Дедлайн в прошлом не принимается (`season.deadlineInPast`); закрыть раньше — шаг 3.
2. После дедлайна ходы игроков закрыты сразу (по часам сервера), а планировщик (`Scheduler:IntervalSeconds`, по умолчанию 5 с; `Scheduler:Enabled`) в течение нескольких секунд переводит сезон в «закрытие». В логе — `season-status-changed` без автора.
3. Досрочно: `POST /api/admin/seasons/{id}/status` с `{commandId, to: "closing"}`.
4. В «закрытии» проверьте все пруфы (очередь `GET /api/admin/seasons/{id}/proofs` пуста). Правки часов, сложности и очков в «закрытии» попадают в итоги.
5. Завершить: `to: "finished"`. Если в очереди остались прохождения — отказ `season.proofsPending`. Итоги сохраняются снимком (таблица `SeasonResult`) и больше не меняются.
6. Архив: `to: "archived"`. Статусы не откатываются.

## Проверить целостность сезона

Проверено руками 2026-09-25: `npm run season:check` на базе сида разработки и на её загруженной копии — «intact».

- С сайта: `GET /api/admin/seasons/{id}/integrity` (админ). Ответ: `isIntact`, `lastSequence`, `settled`, `differences`.
- Локально: `npm run season:check -- <id сезона> [--db <путь к базе>]`; код выхода 0 — цело, 3 — есть расхождения.
- Расхождение — строки вида `player <id>: points, cellId`, `run <id>: in the log, not stored`, `season.result`, `ruleset v2: …`. Это ошибка в коде проекции: выгрузить сезон (ниже), завести баг, таблицы руками не править.
- `settled: false` — пока шла проверка, приходили команды: повторить.

## Выгрузить сезон и загрузить в другую копию

Проверено руками 2026-09-25 на базе сида разработки: выгрузка, загрузка в новую базу, проверка целостности обеих, повторная загрузка отклонена.

1. Выгрузка:
   - с сайта: `GET /api/admin/seasons/{id}/export` (админ) — zip-архив;
   - или локально: `npm run season:export -- <id сезона> <архив.zip> [--db <путь к базе>]` (по умолчанию `var/dev.db` или переменная `GAMEEVENT_DB`).
2. Архив — **закрытые данные**: логины, имена, роли и весь лог сезона (ссылки на пруфы, комментарии). Паролей и их хешей в нём нет. Не выкладывать в открытый репозиторий.
3. Загрузка — **только в локальную или тестовую копию, никогда в боевую базу**: `npm run season:import -- <архив.zip> [--db <путь>] [--allow-role-mismatch] [--with-pool]`.
   - Новая база создаётся с таблицами; в существующую сезон грузится как есть. Сайт на этой базе лучше остановить: загрузка — одна длинная транзакция записи (иначе возможен `SQLITE_BUSY`).
   - Аккаунты сопоставляются по логину; если роль в архиве другая — отказ, пока не передан `--allow-role-mismatch`. Отсутствующие аккаунты создаются удалёнными зрителями без пароля, которым можно войти.
   - Игры сезона добавляются удалёнными, категории не добавляются; `--with-pool` добавляет игры живыми и категории — нужно, чтобы продолжать играть в копии.
4. Архив проверяется до записи (нумерация событий, создание сезона первым, аккаунты и метки отката, пул), загрузка идёт одной транзакцией и сохраняется только при пройденной проверке целостности. Сезон, который уже есть в базе, повторно не загружается.

## Завести аккаунт игроку или зрителю

Не проверено руками (API-тесты `AccountManagementTests`; экран админки — H8).

1. `POST /api/admin/accounts` с `{commandId, login, name, role}` (`player`, `spectator`, `admin`). В ответе — `temporaryPassword`, он показывается один раз: сразу передать человеку.
2. Человек входит с временным паролем и сразу меняет его на свой — до этого сайт ничего больше не открывает.
3. Если ответ потерялся (повтор той же командой вернёт `duplicate: true` без пароля) — сбросить пароль (ниже).
4. Добавить в сезон посреди сезона пока нельзя без разработчика: эндпоинта для `AddSeasonPlayer` ещё нет (API админки — E2, экран — H8).

Не проверено руками (API-тесты `AccountManagementTests`).

`POST /api/admin/accounts/{id}/reset-password` с `{commandId}` → новый `temporaryPassword` (один раз). Все сессии и соединения этого аккаунта обрываются сразу, при входе он снова обязан сменить пароль.

## Сайт упал или ведёт себя странно

Не проверено руками целиком (проверки — `ObservabilityTests`).

1. `GET /health` (без входа): `status` и по проверкам `database`, `disk`, `queue`. 503 — что-то нездорово. Сразу после старта `queue` может несколько секунд быть `unhealthy` — повторить через 5–10 секунд.
   - `database: unhealthy` — база не отвечает или без схемы: миграции (`dotnet run --project src/GameEvent.Web -- migrate`), права на файл, место.
   - `disk: unhealthy` — меньше `Health:MinFreeDiskMb` свободно рядом с базой: освободить место (старые логи и бэкапы).
   - `queue: unhealthy` — потребитель очереди остановился или команда выполняется дольше `Health:MaxCommandSeconds`: смотреть лог, перезапустить сайт; `degraded` — копятся команды, смотреть лог.
   - Подробнее логировать без пересборки: переменная окружения `Logging__LogLevel__Default=Debug` и перезапуск.
2. Загруженные файлы лежат в `var/files` (`Files:Path`); без них пруфы и аватарки — 404 (бэкап и восстановление вместе с базой — раздел J).
3. Логи: `var/logs/game-event-YYYYMMDD.log` (файл в день, до 20 МБ, 30 последних).
4. Последние ошибки с запросом и пользователем: `GET /api/admin/errors` (админ); в логе у каждой — номер ошибки.
5. Если данные выглядят не так — проверка целостности (выше).
