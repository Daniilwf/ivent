# Инструкция по эксплуатации

Ведёт агент. Каждый пункт проверен руками хотя бы раз; непроверенные помечены «не проверено».

Все команды `docker compose` ниже — из корня репозитория на сервере; для краткости `dc` означает `docker compose -f deploy/docker-compose.yml --env-file .env` (на сервере удобно `alias dc='docker compose -f deploy/docker-compose.yml --env-file .env'`). Боевой сервер, домены, внешнее хранилище бэкапов и мониторинг ещё не заведены: это делается в самом конце вместе с заказчиком (J2, J3); всё ниже проверено на Docker своего компьютера (`https://localhost`).

## Развернуть с нуля

Проверено руками 2026-09-26 на Docker Desktop (Windows): чистые тома, `up -d`, миграции, `site` — `healthy`, первый админ, `/health` → «Healthy», вход админом и смена временного пароля.

1. На сервере нужны Docker с плагином compose и git. Склонировать репозиторий, скопировать `.env.example` в `.env`, указать домены (`SITE_DOMAIN`, `STAGING_DOMAIN`; локально оставить `localhost`) и версию (`SITE_VERSION` — тег образа; при выкладке из CI его ставит workflow, J2).
2. `dc up -d --build` — соберётся образ, выполнятся миграции (сервис `migrate` отрабатывает и выходит с кодом 0), поднимутся сайт и Caddy. Тестовая копия: добавить `--profile staging`.
3. Первый админ (один раз, на новом сайте): `dc stop site`, затем `dc run --rm site create-admin admin "Админ"` — временный пароль показывается один раз, при первом входе его нужно сменить; потом `dc start site`. Только через `run --rm` (не `exec` и не `up`): так пароль не остаётся в логах контейнера. При работающем сайте команда откажет — это защита от второй очереди.
4. Проверить: `https://<домен>/health` → «Healthy»; `dc ps` — у `site` статус `healthy`; войти админом, сменить пароль.
5. Сразу сделать первый бэкап и поставить ежедневный в cron (раздел «Бэкапы»).

- Данные сайта — в томе `ivent_site-data` (`/data` в контейнере: база, файлы, логи, ключи сессий, флаг обслуживания); бэкапы — в отдельном томе `ivent_site-backups` (`/backups`), его подключает только разовый сервис `backup`, работающий сайт — нет; у тестовой копии — `ivent_staging-data` и `ivent_staging-backups` (сервис `staging-backup`). `dc down` тома не трогает; `dc down -v` **удаляет данные** — на сервере не использовать.
- Локально браузер предупредит о сертификате Caddy для localhost — это ожидаемо.
- Версии: `SITE_VERSION` — боевой сайт, `STAGING_VERSION` — тестовая копия; при выкладке называть сервисы (`up -d staging-migrate staging` или `up -d migrate site`), чтобы не задеть другой.
- **Разовые команды (`dc run --rm site …`, `dc run --rm backup …`) идут на образе `SITE_VERSION`.** С J3 незнакомая команда отказывает (код 2), но образы до J3 вместо неё запускали второй сайт на тех же данных — так было при проверке 2026-09-26. `SITE_VERSION` в `.env` всегда равен версии, которая сейчас работает; `deploy/backup.sh` сам отказывает, если в образе нет бэкапов (метка `ivent.backup`).
- В `/data/keys` — ключи, которыми подписаны сессии: бэкап — секрет (права 0600); ключи восстанавливаются только на боевом сайте и только с `--with-keys`, в тестовой копии команда откажет.
- На Docker Desktop (Windows) `dc stop site` иногда ждёт минуту-две и пишет «PID … is zombie» — контейнер всё равно останавливается; на Linux-сервере такого не ожидается.

2. Обслуживание: `dc exec site touch /data/maintenance`, подождать 2 секунды (команда, начатая до флага, успевает записаться). Проверка: `curl -s https://<домен>/api/status` → `{"maintenance":true}`.

Не прошёл — выключить обслуживание и не выкладывать. **Первая выкладка с бэкапами (J3):** в работающем образе команд бэкапа ещё нет, скрипт откажет — бэкап делает новый образ: `SITE_VERSION=<новая> deploy/backup.sh --verify` (он только читает данные, миграций не делает).

5. Новый образ: `SITE_VERSION=<новая> dc up -d --no-deps site`, дождаться `healthy` (`dc ps`) и `https://<домен>/health` → «Healthy». Флаг обслуживания лежит в томе — новая версия стартует в обслуживании.
6. Дымовые только на чтение: `npm run test:smoke -- https://<домен>` (со своего компьютера; локально — `E2E_IGNORE_HTTPS_ERRORS=1`). Упали — «Откатить».
7. Выход из обслуживания: `dc exec site rm /data/maintenance`; `/api/status` → `{"maintenance":false}`.
8. Записать новую версию в `SITE_VERSION` в `.env`.

## Бэкапы

Проверено руками 2026-09-26 локально: `deploy/backup.sh --verify --copy-to <папка>` на работающем сайте (архив 87 КБ меньше чем за секунду, проверка «sound», копия на хосте с правами владельца), `npm run backup:verify -- <папка>` на этой копии (перепись 10 непустых таблиц, сезон цел), тот же архив с одним испорченным байтом — «NOT sound», код 3; `Backup__Keep=2` — два старых архива удалены. Повторно 2026-09-27 после ревью (D-214): у работающего `site` смонтирован только `/data`; `SITE_VERSION=local deploy/backup.sh` на образе без бэкапов — отказ, код 1; в обслуживании `deploy/backup.sh --verify --copy-to var/…` — архив, хеш записан в `BACKUP_HASHES`, проверка «sound» с `--sha256`, копия сверена `sha256sum -c`; `dc run --rm site frobnicate` — подсказка, код 2; `dc run --rm --no-deps backup backup-verify` — «sound».

- Что в архиве `backup-<время UTC>.zip`: база (онлайн-бэкап SQLite — согласованный снимок, сайт в это время работает и пишет), загруженные файлы (`files/`), ключи сессий (`keys/`) и `manifest.json` с размером и SHA-256 каждого файла. Под своим именем архив появляется только целиком.
- Архив — **секрет**: хеши паролей всех аккаунтов и ключи сессий. Всё, через что он проходит, создаётся сразу с правами 0600 (папки 0700). Не в открытый репозиторий и не в чаты.
- Сделать: `deploy/backup.sh` (боевой сайт; `deploy/backup.sh staging` — тестовая копия). Работает и при запущенном, и при остановленном сайте: бэкап делает разовый контейнер `backup` того же образа — работающий сайт тома с бэкапами не видит и испортить архив не может. `--verify` — сразу проверить архив; `--copy-to <папка на хосте>` — скопировать его из тома (для внешнего хранилища), рядом — `SHA256SUMS`. Путь к `.env` — `ENV_FILE`, по умолчанию `.env` в корне. Каждая команда ограничена 30 минутами (`timeout`).
- **Хеш каждого архива** скрипт дописывает вне тома: `var/backup-hashes.txt` в корне репозитория (`BACKUP_HASHES`), строка `<sha256>  <архив>`. По нему восстановление проверяет, что архив тот самый (`--sha256`). Этот файл тоже копировать во внешнее хранилище.
- Без Docker: `dotnet run --project src/GameEvent.Web -- backup` (в `var/backups`, хеш — в выводе, строка `SHA-256:`).
- Где лежат: том `ivent_site-backups` (`/backups`; настройка `Backup:Path`). Посмотреть: `dc run --rm --no-deps --entrypoint ls backup -l /backups`.
- Сколько хранится: `Backup:Keep` — по умолчанию 14 последних (`BACKUP_KEEP` в `.env`); лишние удаляются после каждого нового бэкапа. Считаются только файлы вида `backup-<время>Z.zip` и `backup-<время>Z-2.zip`; чужие файлы не трогаются, остатки прерванных бэкапов и проверок (`.backup-*`, `.verify-*`) удаляются, когда им больше часа.
- Когда: перед каждой выкладкой (шаг 3 «Обновить сайт», уже в обслуживании; в J2 — автоматически) и ежедневно cron на сервере: `0 4 * * * cd /srv/ivent && deploy/backup.sh --verify >> /srv/ivent/backup.log 2>&1`.
- После каждого бэкапа в выводе `WARNING …` про папки `before-restore-*`, `failed-restore-*`, `.restore-*` в `/data` старше 7 дней — посмотреть и удалить.
- Проверить, что бэкап восстанавливается (в SPEC — раз в неделю автоматически; с `--verify` в cron — каждый день):
  - на сервере: `dc run --rm --no-deps backup backup-verify [/backups/<архив>] [--sha256 <хеш>]` — без архива последний; рабочая папка — рядом с архивом (`/backups/.verify-*`, 0700), а не в маленьком `/tmp` контейнера;
  - на своём компьютере: `npm run backup:verify` (последний архив в `var/backups` или в `GAMEEVENT_BACKUPS`), `npm run backup:verify -- <архив или папка> [--sha256 <хеш>]`.
  - Проверка сверяет: хеш архива с записанным (если дан); состав, размеры (до распаковки) и хеши по `manifest.json`; `PRAGMA integrity_check` и внешние ключи; что архив не от более новой версии (тогда проверять той версией); что схема базы — ровно та, что дают её миграции (чужие таблицы, индексы, триггеры, представления — отказ); перепись таблиц (как `db-census`, только в `npm run backup:verify`); повтор лога каждого сезона против сохранённого состояния (как `season-check --all`; старый архив сначала догоняется миграциями этой версии на копии); что каждый загруженный файл из базы есть в архиве. Код выхода 0 — «sound», 3 — проблемы (строки `PROBLEM`, в том числе любая ошибка чтения), 1 — архива нет. При проблеме архив не удалять, сделать новый бэкап и разбираться; `npm run backup:verify` оставляет распакованную копию (путь в выводе).
- **Внешнее хранилище** (SPEC: ежедневно за пределы сервера) — в самом конце, с заказчиком: выбрать хранилище, завести доступ, добавить в cron `--copy-to` и отправку архивов и `backup-hashes.txt`. Пока бэкапы лежат на том же диске и от потери сервера не спасают.

## Восстановить из бэкапа

Проверено руками 2026-09-26 локально: после бэкапа заведён ещё один аккаунт; `stop site` → `restore` → `migrate` → `up`: аккаунта нет, сезон цел, загруженный файл открывается, прежние данные — в `before-restore-…`. Повторно 2026-09-27 после ревью: `restore -` со стандартного ввода с копии на хосте — с чужим хешем код 3, ничего не тронуто; `staging-backup restore … --with-keys` — отказ, код 1; с записанным хешем — восстановлено (аккаунт после бэкапа пропал, сезон цел, ключи остались прежними), при работающем сайте — отказ, код 1; `--entrypoint ls` и `--entrypoint rm` из шагов ниже работают.

1. Выбрать архив и его хеш: `grep <архив> var/backup-hashes.txt` (или `SHA256SUMS` рядом с копией).
2. Остановить сайт: `dc stop site` (при выкладке сайт уже в обслуживании — всё равно остановить).
3. Восстановить — обычный путь с хешем:
   - архив в томе: `dc run --rm --no-deps backup restore /backups/<архив> --sha256 <хеш>`;
   - копия с хоста или из внешнего хранилища: `dc run --rm --no-deps -T backup restore - --sha256 <хеш> < <путь к архиву>` — архив читается со стандартного ввода, права и владелец файла на хосте не мешают.
   - Сначала полная проверка (как `backup-verify`, плюс хеш); не прошла — ничего не тронуто, код 3. Прошла — текущие база и файлы перенесены в `/data/before-restore-<время>`, на их место — из архива; каждый файл при распаковке сверяется с манифестом ещё раз. Сорвалось на середине — записанное уходит в `/data/failed-restore-<время>`, прежние данные возвращаются на место, код 1 и оба пути в выводе. При работающем сайте команда откажет.
   - Ключи сессий — только на боевом сайте и только с `--with-keys` (например, после потери сервера, чтобы никого не разлогинило); без него текущие ключи остаются, все входят заново. В тестовой копии (`staging-backup`) `--with-keys` отказывает.
   - **Боевой бэкап в тестовой копии несёт настоящие хеши паролей.** После такого восстановления войти админом тестовой копии и сбросить пароли всем аккаунтам (`POST /api/admin/accounts/{id}/reset-password`), а лучше пользоваться выгрузкой сезона (раздел «Выгрузить сезон»), в которой паролей нет.
4. Миграции этой версией: `dc run --rm migrate` (старый архив догоняется до текущей схемы).
5. `dc up -d --no-deps site`, `/health`, проверка целостности (`GET /api/admin/seasons/{id}/integrity`). Флаг обслуживания — не часть данных, восстановление его не трогает: если он был включён, сайт стартует в обслуживании — выключить после проверок.
6. Всё в порядке — удалить прежние данные: `dc run --rm --no-deps --entrypoint rm backup -r /data/before-restore-<время>`.

- Потеряно всё, что записано после бэкапа (при выкладке — ничего, из-за обслуживания).

## Закрыть сезон

Не проверено руками (появится в админке, H8; пока — через API, как «Начать сезон»).

1. Дедлайн задаётся заранее: `POST /api/admin/seasons/{id}/deadline` с `{commandId, deadline}` (UTC или со смещением, хранится в UTC). Дедлайн в прошлом не принимается (`season.deadlineInPast`); закрыть раньше — шаг 3.
2. После дедлайна ходы игроков закрыты сразу (по часам сервера), а планировщик (`Scheduler:IntervalSeconds`, по умолчанию 5 с; `Scheduler:Enabled`) в течение нескольких секунд переводит сезон в «закрытие». В логе — `season-status-changed` без автора.
3. Досрочно: `POST /api/admin/seasons/{id}/status` с `{commandId, to: "closing"}`.
4. В «закрытии» проверьте все пруфы (очередь `GET /api/admin/seasons/{id}/proofs` пуста). Правки часов, сложности и очков в «закрытии» попадают в итоги.
5. Завершить: `to: "finished"`. Если в очереди остались прохождения — отказ `season.proofsPending`. Итоги сохраняются снимком (таблица `SeasonResult`) и больше не меняются.
6. Архив: `to: "archived"`. Статусы не откатываются.

3. Если ответ потерялся (повтор той же командой вернёт `duplicate: true` без пароля) — сбросить пароль (ниже).

## Режим обслуживания

- Включить: создать файл `maintenance` рядом с базой (по умолчанию `var/maintenance`; в контейнере — в томе с базой), например `touch var/maintenance`, или админом `PUT /api/admin/maintenance {"on": true}`. Выключить: удалить файл или `{"on": false}`. Изменение видно сразу, перезапуск не нужен.
- Пока режим включён: сайт читается, любая запись отвечает 503 «Идёт обслуживание», на страницах баннер; вход и выход работают; дедлайн, наступивший во время обслуживания, сработает сразу после выключения.
- Проверить: `GET /api/status` → `{"maintenance": true}`.
- При выкладке: после `touch` подождать 2 секунды (команда, начатая до флага, успевает записаться), потом бэкап и миграции. Во время выкладки не выключать режим с сайта.

## Выгрузить сезон и загрузить в другую копию

Проверено руками 2026-09-25 на базе сида разработки: выгрузка, загрузка в новую базу, проверка целостности обеих, повторная загрузка отклонена.

1. Выгрузка:
   - с сайта: `GET /api/admin/seasons/{id}/export` (админ) — zip-архив;
   - или локально: `npm run season:export -- <id сезона> <архив.zip> [--db <путь к базе>]` (по умолчанию `var/dev.db` или переменная `GAMEEVENT_DB`).
2. Архив — **закрытые данные**: логины, имена, роли и весь лог сезона (ссылки на пруфы, комментарии). Паролей и их хешей в нём нет. Не выкладывать в открытый репозиторий.
3. Загрузка — **только в локальную или тестовую копию, никогда в боевую базу**: `npm run season:import -- <архив.zip> [--db <путь>] [--allow-role-mismatch] [--with-pool]`.
   - Новая база создаётся с таблицами; в существующую сезон грузится как есть. Сайт на этой базе лучше остановить: загрузка — одна длинная транзакция записи (иначе возможен `SQLITE_BUSY`).
   - Аккаунты сопоставляются по логину; если роль в архиве другая — отказ, пока не передан `--allow-role-mismatch`. Отсутствующие аккаунты создаются удалёнными зрителями без пароля, которым можно войти.
   - Игры сезона добавляются удалёнными, категории не добавляются; `--with-pool` добавляет игры живыми и категории — нужно, чтобы продолжать играть в копии.
4. Архив проверяется до записи (нумерация событий, создание сезона первым, аккаунты и метки отката, пул), загрузка идёт одной транзакцией и сохраняется только при пройденной проверке целостности. Сезон, который уже есть в базе, повторно не загружается.

- В образе: Workstation GC (`DOTNET_gcServer=0`) и режим экономии памяти (`DOTNET_GCConserveMemory=7`). Лимиты контейнеров в `deploy/docker-compose.yml`: сайт — 512 МБ ОЗУ и до 256 МБ подкачки, 1 ядро; тестовая копия — 384 МБ, половина ядра; Caddy — 128 МБ; разовые команды (миграции, бэкап) — 384 МБ.
- **Файл подкачки** на сервере (1–2 ГБ), один раз при настройке:
  ```sh
  sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
  sudo mkswap /swapfile && sudo swapon /swapfile
  echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
  echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-swappiness.conf && sudo sysctl --system
  ```
- **Тестовая копия** запускается только на время проверки и останавливается после: `docker compose --profile staging up -d staging` → проверка → `docker compose stop staging`.
- **Замер**: `npm run test:memory [-- --seconds 120 --budget 400 --image <образ>]` (нужен Docker): засевает демо-сезон, запускает образ с лимитами боевого сайта, 16 игроков ходят по страницам, память контейнера снимается каждые 2 с. Пик выше бюджета — выпуск останавливается. Входит в `/release`.
