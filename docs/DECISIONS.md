## Закрытые вопросы

Ответы заказчика от 2026-09-24.

- **Q-1. Структура репозитория и git.** Комплект перенесён в корень, `games.xlsx` — в `data/import/` (не в git), дубли удалены, `git init`, `main`, `gh` установлен и авторизован. Репозиторий на GitHub **публичный**. Следствия: секреты только в GitHub Secrets и `.env`, gitleaks в pre-commit и CI обязателен, в git не попадают ники игроков из таблицы (см. D-30), личные данные в сидах заменены.
- **Q-2. Монетки на этапе 1 — вариант (а).** Монетки начисляются за прохождение по `reward.coins`, платный реролл стоит монеток по `roll.rerollCost`. На этапе 1 монетки тратятся только на рероллы. Конфиг по умолчанию не меняется.
- **Q-3. Реджект и правки у финишировавшего — принято как предложено.**
  - Позиция финишировавшего складывается только из прохождений до финиша, прохождения после финиша позицию не двигают.
  - Реджект или правка часов любого прохождения до финиша пересчитывает позицию. Если игрок больше не дотягивает до финиша, финиш снимается: бонус финиша снимается, игрок снова активен, места пересчитываются (Q-4). Если дотягивает — финиш остаётся.
  - Первое место окончательное, когда одобрены пруфы всех прохождений игрока до финиша включительно. Все они поднимаются в начало очереди пруфов.
  - Прохождения первого после заморозки дают 0 очков, их реджект ничего не снимает. У остальных реджект снимает очки как обычно.
- **Q-4. Бонусы финиша при пересчёте мест пересчитываются у всех финишировавших** по новому порядку финиша компенсирующими событиями, итог в логе. «Бонус один раз» = в каждый момент у игрока не больше одного бонуса финиша.
- **Q-5. Смена сложности после броска: пересчёт каждого кубика по формуле** `новое = ⌈старое × новые грани / старые грани⌉`. В событии хранятся оба значения каждого кубика («было/стало») и оба типа кубика. Очки и клетки корректируются разницей. Повтор лога детерминирован, случайности нет. Если сложность была «выше сложной» и ручной эффект «хороший ивент» ещё ждёт, он помечается «не применимо» с комментарием; если уже применён — остаётся, админ правит вручную.
- **Поправка к заморозке первого финишировавшего** (уточняет SPEC «очки замораживаются на момент его финиша» и P4, SE7):
  - Пока первый финиш на проверке (предварительный), очки и монетки игрока считаются как обычно, включая штраф за дроп по очкам. Позиция уже фиксирована.
  - Влиять на других предварительный первый уже не может: он вне целей и не использует предметы на других, его прохождения не делают игру «пройденной в сезоне» (D-16).
  - Заморозка наступает при одобрении: с этого момента очки и монетки не меняются, инвентарь заморожен.
  - Если первого реджектнули и первым стал следующий финишировавший, он замораживается в момент, когда стал первым (если его финиш уже подтверждён) или при одобрении своего финиша. Его бонус финиша снимается. Очки на момент финиша не хранятся и не восстанавливаются: всё, что он набрал между финишем и заморозкой, остаётся.
- **K-1. Финиш и места — этап 1**, как решено в таблице противоречий.

## Решения этапа 1

Дата всех решений ниже — 2026-09-24, если не указано иное.

### Движок

- **D-01. Контракт движка — decider.** `Decide(state, command, ctx) → события | отказ` и чистая `Apply(state, event) → state`. `ctx` содержит `IClock`, `IRandomSource`, `IIdGenerator` и `IPoolView` (игры и категории, только чтение); правила сезона — в состоянии (уточнено D-82). Почему: повтор лога — это просто свёртка `Apply` без случайности и пула. Так же устроены проверка целостности, откат и симулятор.
- **D-02. Идентификаторы в движке** генерирует `IIdGenerator`, а не `Guid.NewGuid`. Сгенерированные id записываются в события. Почему: детерминированный повтор и запрет анализатора.
- **D-03. Позиция — строковый id клетки (`CellId`), а не число.** Линейная карта — клетки `start`, `c1`…`c{N-1}`, `finish`, где N = `map.linearLength` (число шагов от старта до финиша). «Клеток до финиша» считается по графу. Почему: CONTENT.md использует строковые id клеток, на этапе 2 карта станет свободным графом.
- **D-04. Ролл и прохождение.** Команда «Крутить колесо» переводит игрока в `Rolling` с предложенной игрой, снапшот фиксируется в этот момент. Прохождение (`Run`) создаётся командой «Начать» (`Rolling → Playing`) с этим снапшотом. Окно тех-реролла отсчитывается от ролла этой игры. Предложенная игра зарезервирована: другим она выпадает как промах «Сейчас играет».
- **D-05. Алгоритм ролла.** Доступные игры = пул без удалённых, без пройденных в сезоне, без занятых, без исключений игрока, под фильтрами. Колесо крутится по категориям, где есть хотя бы одна доступная игра, по весам. Затем сервер перемешивает все неудалённые игры категории, кроме исключений игрока, и тянет по одной. Недоступная по сезонной причине («Уже прошёл Вася», «Сейчас играет Вася») записывается как промах, первая доступная выбирается. Своё исключение молча пропускается, по таблице статусов игрок его не видит. Цикл конечен, потому что в категории гарантированно есть доступная игра.
- **D-06. `choiceCount > 1`**: одна категория, N разных доступных игр из неё (меньше, если столько нет), выбор через `PendingChoice`. Все варианты зарезервированы до выбора.
- **D-07. Бесплатные рероллы**: `roll.freeRerollsPerRoll` на каждый ролл, отдельно ресурс `freeRerolls` в словаре ресурсов (так работает «Купон реролла» из CONTENT.md). Сначала тратятся бесплатные за ролл, потом ресурс, потом платный реролл по `rerollCost`. «Уже проходил» и промахи бесплатны и рероллом не считаются. Новый ролл после тех-реролла — это новый ролл со своими бесплатными рероллами.
- **D-08. «Уже проходил» без лимита**, на совести, видно в логе. Исключение действует в пределах сезона (`PlayerGameExclusion` принадлежит игроку сезона).
- **D-09. Дроп**: разрешён в `Playing` в любой момент, `minPlayMinutesBeforeDrop` — только предупреждение в интерфейсе. Очки могут уйти в минус: иначе ранний дроп бесплатен, а «Бесплатный дроп… дроп отнимает очки». Позиция не ниже старта (на этапе 2 — не ниже последнего пройденного чекпоинта). У финишировавших не первыми и у предварительного первого штраф бьёт только по очкам, плохой ивент создаётся как обычно (он действует на самого игрока). У замороженного первого (финиш одобрен) штрафа и ивента нет. Обновлено 2026-09-24 по поправке к заморозке.
- **D-10. Плохой и хороший ивенты на этапе 1** создаются базовым действием `drawEvent`. При выключенном `features.events` оно создаёт ручной эффект «Разыграй плохой/хороший ивент». На этапе 5 то же действие начнёт тянуть карту из колоды без изменения мест вызова.
- **D-11. Тех-реролл**: причина из списка (`weakPc`, `paidUnavailable`, `doesNotLaunch`, `emulatorTooSlow`, `other` + текст обязателен для `other`). После окна — только админ, от имени игрока, с отметкой в логе. Превратить в дроп админ может в любой момент до завершения сезона. Штраф бьёт по текущим очкам и позиции, исключение меняет причину на дроп.
- **D-12. Завершение — одна команда**: сложность, часы (если в снапшоте их нет — оценка и ссылка на источник), отметка «челлендж выполнен», пруф необязателен. Кубы кидаются в той же команде, затем движение. На этапе 4 между броском и движением встанет окно `afterDice` через `PendingChoice`, если у игрока есть подходящие предметы; при выключенных предметах шаг пропускается.
- **D-13. Число кубов**: `hours / hoursPerDie`, округление по `rounding` (`nearest` — половина вверх, `MidpointRounding.AwayFromZero`), затем пределы `min`…`max`. Челлендж прибавляет `challengeBonus.extraDice` после ограничения. Проверка челленджа — вместе с пруфом.
- **D-14. Конвейер броска** есть с этапа 1: этапы `count → sides → roll → reroll → add → multiply → min/max`, у модификатора этап и приоритет. Кубики хранятся по отдельности, прибавки — отдельно от кубиков. При правке часов меняется только этап `count`: недостающие докидываются, лишние снимаются с конца, прибавки сохраняются.
- **D-15. Реджект**: снимаются очки и клетки этого прохождения (с учётом последующих правок). Игра больше не считается пройденной и возвращается в пул всем, включая этого игрока. Реджект — обычная команда, её можно откатить.
- **D-16. Свободный режим первого финишировавшего** начинается в момент финиша первым (предварительного): игра, которую он играет, занята (двое одну игру не играют), но его прохождение не делает игру «пройденной в сезоне» для остальных, потому что он не влияет на гонку. Движения нет: позиция фиксирована. Очки и монетки: до одобрения финиша — как обычно, после одобрения (заморозки) — ноль событий. У прохождения хранится признак `FreeMode` на момент завершения (в событии `RunCompleted`, D-99); если финиш потом снят, уже завершённые в свободном режиме прохождения остаются не блокирующими игру. Обновлено 2026-09-24 по поправке к заморозке.
- **D-17. Тайбрейк `earliestFinalScore`**: момент последнего изменения очков игрока (по порядку событий). У кого он раньше, тот выше.
- **D-18. Несколько сезонов одновременно** разрешены в движке и БД: каждый E2E-тест создаёт свой сезон. Интерфейс показывает «текущий» сезон пользователя (последний идущий, где он участвует), админ выбирает сезон в админке.
- **D-19. Категории и пул** глобальные, между сезонами. Правки весов и игр пишутся в глобальный лог админских действий (`GameEvent` без сезона) и не откатываются через откат сезона.
- **D-20. Зависимости для отката**: у каждого события есть набор ключей, которые оно затрагивает (`player:{id}`, `run:{id}`, `game:{seasonId}:{gameId}`, `finishOrder:{seasonId}`, `season:{id}`). Более поздняя неотменённая команда с пересечением ключей — зависимая. Откат отказывает и показывает её. Откат отката не поддерживается: действие просто делают заново.
- **D-21. Правка игрока админом** (позиция, очки, монетки, ресурсы, фаза хода) — команда с событиями-дельтами, поэтому инвариант «очки = сумма изменений» выполняется. Новый игрок посреди сезона: форма предзаполнена нулями и стартом, админ меняет. Предлагаемый дефолт — отдельное поле конфига `season.newPlayerDefaults` (см. открытый вопрос SPEC).
- **D-22. Флаги функций**: каждая команда и каждое базовое действие объявляет нужный флаг. При выключенном флаге — отказ без событий. Валидация конфига не даёт включить механику, которой нет в сборке (на этапе 1 все флаги, кроме `mapMode: linear`), с понятной ошибкой.
- **D-23. Конфиг**: C#-записи с дефолтами, схема — `System.Text.Json.Schema.JsonSchemaExporter` (встроен в .NET, без сторонних пакетов), плюс семантическая проверка (`min ≤ max`, грани ≥ 2 и т. п.). Версия конфига — строка `RulesetVersion` на сезон. История «было/стало» строится сравнением JSON по путям и подписями полей из словаря интерфейса.
- **D-24. Лимиты цепочки эффектов** реализуются в диспетчере триггеров уже на этапе 1 и проверяются тестовыми эффектами из тестовой сборки. Боевых подписчиков на этапе 1 нет.

### Инфраструктура и веб

- **D-25. Картинки — NetVips (libvips)**: WebP с ограничением разрешения, анимированные GIF → уменьшенная анимированная миниатюра для карты, тип по содержимому. Почему: мало памяти на VPS 1 ГБ, анимация; ImageSharp — нестандартная лицензия, SkiaSharp не делает анимированные миниатюры.
- **D-26. Пароли** — `PasswordHasher` из ASP.NET Core Identity (PBKDF2) без всей Identity. Куки `HttpOnly`, `Secure`, `SameSite=Strict`, антифорджери-токен в заголовке для SPA, ограничение попыток по логину и IP встроенным `RateLimiter`.
- **D-27. Миграции** запускаются отдельной командой приложения (`GameEvent.Web migrate`) отдельным шагом деплоя, не при старте.
- **D-28. Обложки**: Steam Store search (без ключа), IGDB — только если заданы `IGDB_CLIENT_ID`/`IGDB_CLIENT_SECRET`. Файл скачивается и хранится у нас, заглушка рисуется на фронтенде из названия.
- **D-29. HowLongToBeat** — отдельная реализация `IHoursProvider` за переключателем в переменных окружения, с таймаутом и кэшем в БД. Ошибка превращается в «часов нет», и игрок вводит оценку. По умолчанию выключен.
- **D-30. Демо-пул для CI**: `data/import/` не в git, поэтому для демо-сезона и CI коммитим `content/pool.demo.json` — названия, теги, заметки из таблицы без авторов (авторы заменены на «Автор N»). Боевой пул грузится импортом из xlsx.
- **D-31. Ручные эффекты** разрешает игрок-владелец (свои) или админ (любые): «применено» или «не применимо» с комментарием.
- **D-32. Экспорт сезона** — zip: `season.json` (сезон, версии конфига, игроки по логинам, лог событий, снимок состояния), `games.json` (упомянутые игры), по желанию `files/`. Импорт создаёт новый сезон и сопоставляет пользователей по логину, отсутствующих — как неактивные заглушки. После импорта автоматически запускается проверка целостности.
- **D-33. Playwright MCP в этой сессии не подключён.** Исследовательское тестирование идёт скриптами Playwright со скриншотами в `test-artifacts/`, которые агент просматривает сам. Подключить MCP: `claude mcp add playwright npx @playwright/mcp@latest`.

### Инструменты (блок A)

- **D-34. Решение — `GameEvent.slnx`**, а не `.sln`: формат по умолчанию в .NET 10 SDK, короче и без GUID. Все команды работают с ним.
- **D-35. xUnit v3 в режиме VSTest** (`UseMicrosoftTestingPlatformRunner=false`, `IsTestingPlatformApplication=false` в `Directory.Build.props`). Почему: Stryker.NET и coverlet.collector надёжно работают с VSTest; на .NET 10 SDK режим MTP требует переключения всего `dotnet test`. Вернуться к MTP можно одной правкой, когда Stryker его поддержит.
- **D-36. `nuget.config` в репозитории только с nuget.org** и сопоставлением источников: сборка не зависит от источников, настроенных на машине разработчика (на этой машине есть приватный источник с 401).
- **D-37. LF во всех файлах**, включая рабочую копию Windows (`* text=auto eol=lf`, `end_of_line = lf`): иначе `dotnet format` и Prettier спорят с CI.
- **D-38. gitleaks — закреплённый релиз**, скачивается скриптом `scripts/gitleaks.mjs` в `.tools/` с проверкой SHA-256, прописанной в скрипте. Одинаково в pre-commit и CI, без установки в систему и без gitleaks-action.

### Движок (срез B1)

- **D-44. Оценка часов при завершении** (`CompleteRun.EstimatedHours`) используется только если в снапшоте часов нет или они ≤ 0 (иначе игрок застрял бы в `Playing`). Если часы в снапшоте есть, оценка игнорируется, а не отклоняется: источник истины — пул на момент ролла, поправить часы может админ (C7). Оценка ≤ 0 — отказ `run.invalidHours`.
- **D-45. Игра принадлежит категории**, если среди её тегов есть имя категории (без учёта регистра). Игра с несколькими тегами участвует в нескольких категориях — поэтому выпадает чаще (SPEC «Уточнения»: Ролл).
- **D-46. Вытягивание игры из категории** — без возвращения: сервер берёт случайную из оставшихся, недоступную записывает промахом и тянет дальше. Это эквивалентно перемешиванию из D-05, но тратит по одному вызову генератора на попытку. Приоритет причин промаха: «уже пройдена» важнее «сейчас играет».
- **D-47. `PlayerMoved` не пишется, если фишка не сдвинулась** (стоит на финише). `Steps` в событии — полная сумма кубов, путь — клетки, в которые фишка вошла; лишние шаги сгорают.
- **D-48. В логе `null` пишется явно.** Пропуск null-полей при записи ломал чтение обязательных параметров конструктора (поймано тестом круга сериализации).
- **D-49. Формат лога — `StoredEvent(Type, Version, Data)`**: стабильное имя типа, версия формата и JSON данных отдельно (для колонок `GameEvent`). `EventCodec.Decode` прогоняет старые версии через цепочку преобразований; событие новее сборки, без преобразования или неизвестного типа — `JsonException`. Эталонный JSON каждого типа зафиксирован тестом `EventFormatTests`: переименование свойства или значения перечисления роняет его.
- **D-50. Новые поля событий и снапшота всегда необязательные** (nullable или со значением по умолчанию в C#), иначе старые записи лога перестанут читаться при `RespectRequiredConstructorParameters`. Если поле обязательно по смыслу — новая версия события и преобразование.
- **D-51. Кириллица в логе не экранируется** (`JavaScriptEncoder` с `UnicodeRanges.All`, HTML-символы по-прежнему экранируются): лог читается в SQLite глазами.
- **D-52. Тесты движка идут на закреплённом тестовом конфиге** (`Support/TestRuleset`), а не на `docs/ruleset.default.json`: числа по умолчанию временные, ребаланс не должен ронять тесты механик. Отдельные тесты проверяют, что встроенный конфиг совпадает с файлом в `docs/` и играбелен этой сборкой.
- **D-53. Сезон не создаётся с механикой, которой нет в сборке** (`RulesetSupport`; с C1 — ошибка проверки `ruleset.invalid` с путём к полю, D-83): `mapMode: graph` (этап 2), `choiceCount ≠ 1` (снято в C4, D-91), `maxActiveRunsPerPlayer ≠ 1` (отложено, D-91). С C1 проверка идёт при `CreateSeason` и `ChangeRuleset`: невалидный конфиг в лог не попадает, поэтому проверять его на каждой команде больше не нужно (тест «правка посреди сезона отклоняет команды» заменён тестом «правка на нереализованную механику отклоняется»). Каждая проверка снимается своей задачей. Полная валидация конфига при сохранении — C1.
- **D-54. Билдер сценариев строгий**: отказ игрового шага (`Roll`, `Start`, `Complete`) бросает исключение, если тест не вызвал `ExpectRejection()`. Так отказ в середине цепочки не прячется за проверкой последнего шага.
- **D-55. `PlayerMoved` и `PointsChanged` ссылаются на прохождение и причину** (`MoveReason`, `PointsReason`, `RunId`): реджект (C8) снимает клетки и очки именно этого прохождения, пересчёт позиции финишировавшего (Q-3) идёт по прохождениям. Нулевое изменение очков не пишется.
- **D-56. `RunStarted` и прохождение хранят момент ролла** (`RolledAt`): окно тех-реролла (D-04) и окно ставок считаются от ролла, а не от старта.
- **D-57. Доступность игры считается одним предикатом для игрока** (`SeasonGameStatus.For(state, player)`: доступна / промах / скрыта). Колесо и вытягивание используют его оба, поэтому категория на колесе всегда содержит доступную игру. Личные исключения (дроп, тех-реролл, «Уже проходил») станут «скрыта» в C5–C6. Категории на колесе упорядочены по имени: одно зерно даёт один лог независимо от порядка из БД.
- **D-58. Цепочка поставки (по ревью безопасности 2026-09-24).** Actions закреплены полным SHA с комментарием версии, Dependabot обновляет SHA; `actions/checkout` без сохранения токена; у npm и NuGet в Dependabot задержка 7 дней на свежие версии; бинарник gitleaks не запускается, если под `.tools/` есть файлы в git; аргументы оболочки Windows с `%` и `"` отклоняются; в корневом `.gitignore` логи, бэкапы, ключи и таблицы. На будущее: в тестовом сиде никогда нет реальных паролей и данных игроков (трассы Playwright — публичные артефакты), дымовые тесты против боевого сайта — без трасс и скриншотов.

### Инфраструктура (срез B2)

- **D-59. Таблицы среза B2.**
  - `GameEvent`: номер в логе сезона без пропусков, уникальный индекс `(SeasonId, Sequence)`, индекс по `CommandId`, тип команды (`CommandType`), `Type`/`Version`/`Data` из `EventCodec`, `UndoneByEventId` для отката (C12). Глобальные события админа (пул, категории, D-19) пишутся в отдельный лог с `SeasonId = Guid.Empty`, чтобы уникальный индекс действовал и для них (NULL в уникальном индексе SQLite не сравниваются).
  - `Season`, `SeasonPlayer`, `Run`, `Game`, `Category`. `SeasonPlayer.Id` — id участия в сезоне, а не пользователя; `UserId` с уникальным `(SeasonId, UserId)` появится с пользователями в B3. Проекция отказывает, если строка игрока или прохождения принадлежит другому сезону.
  - Время — полные UTC-тики (свой конвертер): сортируется в SQL и читается без потери точности, иначе проекция расходится с логом. Перечисления — строки. `decimal` (часы) SQLite хранит текстом: по нему не сортируем и не фильтруем в SQL. Теги игры — JSON, ролл фильтрует в памяти.
  - Статус сезона пока строка (`Active`); перечисление `SeasonStatus` появится в C10.
  - Полная модель — D1. До первого релиза схема меняется свободно (миграция `Initial` пересоздаётся); после — только расширяющие миграции.
- **D-60. Проекция пишется разницей состояний**: после `Execute` сравниваются игроки и прохождения «до» и «после», меняются только изменившиеся строки, в той же транзакции, что события. Проекция — для чтения (API, лидерборд); источник истины — лог. Исключение: `Season.RulesetJson` — исходные данные (конфиг, по которому играет сезон), а не проекция; до таблицы `Ruleset` с версиями и историей (C1) он хранится только там.
- **D-61. Очередь — `CommandBus` + `CommandProcessor`** (канал с одним читателем, фоновая служба).
  - Кэш состояния сезона в памяти; при первом обращении и после любого сбоя (в том числе сбоя самого коммита, когда неизвестно, записалась ли команда) состояние восстанавливается повтором лога из БД. Кэш заменяется только после коммита.
  - Сезон команды задаёт конверт; `CreateSeason` с другим id отклоняется (`season.mismatch`), состояние другого сезона после команды — ошибка без записи.
  - Повторный `CommandId` того же типа и сезона возвращает уже записанные события без выполнения; тот же id у другой команды или сезона — отказ `command.idReused`. Отклонённые команды не пишутся и при повторе выполняются снова.
  - Вызывающий может перестать ждать (отмена запроса) — команда всё равно выполнится, повтор вернёт её события. При остановке сервера недовыполненные и ждущие команды завершаются отменой, ничего не записав.
  - Слушатели после коммита (SignalR в B3) не могут превратить закоммиченную команду в ошибку.
  - Пишут в БД и открывают транзакции только `CommandProcessor` и миграции (архитектурный тест `DatabaseWriteTests`). Пул пока заполняют тесты и сид напрямую — при появлении сида и импорта (F1, F2) они добавляются в тест осознанно, админские правки пула (E2) пойдут через очередь глобальными командами.
- **D-62. SQLite**: `journal_mode=WAL` ставится при миграции (сохраняется в файле), на каждое соединение — `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=NORMAL`. Всё проверено тестом.
- **D-63. Интеграционные тесты инфраструктуры** (очередь, транзакции, миграции) лежат в `GameEvent.Web.Tests/Queue/…` на настоящем файле SQLite: отдельного тестового проекта инфраструктуры в структуре CLAUDE.md нет. Часы в тестах стоят на моменте с дробными тиками, чтобы ловить потерю точности. Ключевые тесты проверены мутациями: без транзакции, без сброса кэша после сбоя коммита и со старым конвертером времени они падают.
- **D-64. Сгенерированные миграции EF** помечены в `.editorconfig` как сгенерированный код: стиль и анализаторы проекта к ним не применяются, руками они не правятся. Соответствие модели и миграций проверяет тест (`HasPendingModelChanges`).

### Веб (срез B3)

- **D-65. Игрок сезона связан с пользователем**: `AddSeasonPlayer(PlayerId, UserId, Name)`, `UserId` хранится в событии и состоянии. Пользователь участвует в сезоне не больше одного раза (отказ `player.alreadyAdded`, уникальный индекс `(SeasonId, UserId)`). `PlayerId` — id участия. Внешнего ключа `SeasonPlayer.UserId → User` нет сознательно: пользователи удаляются мягко, а импорт сезона (D-32) может принести участников, чьих аккаунтов на этом сайте нет.
- **D-66. Аккаунты**: таблица `User` (логин, нормализованный логин в нижнем регистре — уникальный, имя, хэш пароля, одна роль на аккаунт — у играющего админа два аккаунта, признак обязательной смены пароля, мягкое удаление). До D8 аккаунты создаёт только сид разработки (`seed-dev`) и тесты; сид — осознанно разрешённый писатель в `DatabaseWriteTests`.
- **D-67. Вход** (уточняет D-26):
  - кука `ge.session`: `HttpOnly`, `SameSite=Strict`, `Path=/`, 30 дней со скользящим продлением. Везде, кроме Development и Test (тестовая копия тоже), — `Secure` и префикс `__Host-`; так же кука антифорджери;
  - каждый запрос перечитывает аккаунт: удалённый аккаунт, сменённая роль или новая метка безопасности (`SecurityStamp`, меняется при смене пароля, роли и удалении — D8) завершают сессию сразу. Открытое WebSocket-соединение хаба живёт до переподключения — закрытие соединений при смене метки делает D8;
  - API отвечает 401/403, без перенаправлений на страницу входа;
  - все `POST` под `/api`, включая вход, требуют антифорджери-токен в заголовке `X-CSRF-TOKEN` (`GET /api/auth/antiforgery`); после входа токен запрашивается заново — он привязан к пользователю;
  - попытки входа ограничены по IP фиксированным окном (`Security:LoginAttemptsPerMinute`, по умолчанию 10 в минуту, 429; IPv6 — по префиксу /64) по паре «логин + адрес» (`Security:LoginFailuresPerAddress` за `Security:LoginFailureWindowMinutes`, по умолчанию 5 за 15 минут) и мягко по логину в целом (`Security:LoginFailuresPerLogin` в час, по умолчанию 50). Жёсткий лимит по паре останавливает подбор, но не даёт чужому адресу запереть владельца; окна временные. Попытка резервируется до проверки пароля — параллельные запросы не проскакивают лимит; пустые записи удаляются; неудачи пишутся в журнал (логин и адрес, без пароля);
  - для неизвестного логина всё равно проверяется пароль против фиктивного хэша, чтобы время ответа не выдавало существование логина.
- **D-68. Контракт игровых эндпоинтов**: `POST /api/seasons/{id}/roll|start|complete` с `commandId` от клиента (повтор — тот же ответ с `duplicate: true`). Игрок берётся из сессии, в запросе его нет. Игровые действия — только роль «игрок» и только участник сезона (иначе 403); неизвестный сезон — 404; невалидный ввод — 400; отказ движка — 409 с `code` из `RejectionCodes`. `GET /api/seasons/{id}` виден любому вошедшему (лог публичен), блок `me` — только участнику. Клиент API генерируется**: OpenAPI-документ пишется при сборке `GameEvent.Web` только с `-p:GenerateApiDocs=true` (`Microsoft.Extensions.ApiDescription.Server`), типы — `openapi-typescript` в корневом `package.json` (ему нужен TypeScript 5, у фронтенда 6). `web/src/api/openapi.json` и `schema.d.ts` в git, не форматируются; CI перегенерирует и падает на расхождении.

Команды приложения: `migrate` (миграции отдельным шагом, D-27) и `seed-dev` (только Development: аккаунты `admin`, `vasya`, `petya`, `masha`, `zritel` с паролем из `appsettings.Development.json`, пул из `content/pool.dev.json`, сезон через очередь).

- **D-72. Защита на уровне веба.** Адрес клиента из `X-Forwarded-For` принимается только от сетей из `Proxy:KnownNetworks` (сеть контейнера Caddy, `ForwardLimit = 1`); без настройки заголовок игнорируется — подделкой нельзя обойти лимит входа. Заголовки на всех ответах: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` (полная CSP — вместе с раздачей фронтенда), `Referrer-Policy`; HSTS вне Development и Test. OpenAPI-документ отдаётся только в Development и Test (он и так в репозитории). `appsettings.Development.json` с паролем сида не попадает в публикацию; в Dockerfile (J1) явно `ASPNETCORE_ENVIRONMENT=Production`, в боевом конфиге `AllowedHosts` — домен сайта. В Production при пустом `Proxy:KnownNetworks` в журнал пишется предупреждение; сеть Caddy прописывается в `.env.example` и RUNBOOK (J1).

Клиент API** — `openapi-fetch` на сгенерированных типах (`web/src/api/schema.ts`: генератор с `--enum-values` пишет значения перечислений, поэтому `.ts`, а не `.d.ts`), промежуточный слой добавляет антифорджери-токен ко всем не-GET; `fetch` берётся при каждом вызове (подменяется в тестах). ### Конфиг (C1)

- **D-82. Правила сезона живут в логе.** `CreateSeason(SeasonId, Ruleset)` несёт весь конфиг, `SeasonCreated` его хранит (версия 1), `ChangeRuleset` → `RulesetChanged(Version, Ruleset)` с версией +1. Действующие правила и номер версии — в состоянии сезона, `EngineContext` больше не содержит конфига. `Season.RulesetJson` — теперь проекция из лога, исключение из D-60 снято. Снапшот прохождения хранит номер версии правил сезона (`RunSnapshot.RulesetVersion`). Поле `version` внутри JSON — версия формата документа, а не номер версии правил сезона. Правка `map.linearLength` посреди сезона карту не перестраивает (карта фиксируется при создании; этап 2 — редактор); страница правил показывает длину настоящей карты сезона (H7). Модель данных SPEC соблюдена: таблица `Ruleset` (сезон, версия, конфиг, дата, автор) — проекция событий правил, пишется в транзакции команды. Правка правил не откатывается компенсирующим событием (C12): снапшоты прохождений ссылаются на версию, поэтому «откат» — это новая версия со старым конфигом. В каких статусах сезона правила можно менять, решает C10. Тот же конфиг ещё раз — отказ `ruleset.unchanged`; возврат к старому конфигу — новая версия.
- **D-83. Конфиг проверяется в три слоя.** (1) Разбор `RulesetJson.Parse` строгий: неизвестные поля, отсутствующие обязательные, неверные перечисления и числа строками — ошибка с путём к полю. Строгость только для конфига от админа (`RulesetJson.Options`), конфиги уже в логе читаются мягко. (2) `RulesetValidator.Validate` — смысловые правила (min ≤ max, у кубика не меньше двух граней, неотрицательные бонусы и веса, доля коопа в (0; 1], шаги ставок по возрастанию с открытым последним и т. д.) и нереализованные механики (D-22/D-53: `mapMode: graph`, `choiceCount ≠ 1`, `maxActiveRunsPerPlayer ≠ 1`, любой включённый флаг функции), все ошибки сразу, каждая с путём. (3) Движок отклоняет невалидный конфиг в `CreateSeason` и `ChangeRuleset` (`ruleset.invalid`). Числовые поля ещё не реализованных механик (ставки, магазин, эффекты) проверяются, когда появится механика.
- **D-84. JSON-схема конфига генерируется из C#-типов** (`RulesetSchema.Generate`, `JsonSchemaExporter` со строгими массивами и запретом лишних полей) и лежит в `docs/ruleset.schema.json`. Тест сравнивает файл с генерацией; обновить: `UPDATE_RULESET_SCHEMA=1 dotnet test src/GameEvent.Engine.Tests --filter Schema_is_up_to_date`. Генератор в движке — им же воспользуется редактор конфига в админке (H8).
- **D-85. «Было/стало»** — `RulesetDiff.Between`: изменения на уровне листьев, путь с индексами массивов, значения JSON-текстом, по порядку путей. API: `GET /api/seasons/{id}/rules` (любой вошедший) — действующие правила и история версий (новые первыми) с датой и автором из лога; `PUT /api/admin/seasons/{id}/rules` (только админ) — тело целиком новый конфиг, ошибки разбора и проверки — 400 со списком `{path, message}`, отказ движка — 409. Подписи полей для страницы правил — из словаря интерфейса (H7).
- **D-86. Границы и формат конфига.** Поле `version` — версия формата документа, сейчас 1; другое значение — ошибка (`RulesetValidator.CurrentFormat`). Защитные потолки против опечаток — не баланс, поэтому в коде: карта до 10 000 шагов, кубов и штрафных кубов до 1 000, граней до 1 000. Часовой пояс проверяется по системной базе поясов IANA в веб-слое перед командой (движку нельзя читать систему); в образе Docker нужна база поясов (J1). Правка правил админом: тело `{commandId, expectedVersion, ruleset}` — повтор с тем же id не меняет дважды, правка с устаревшей версией — отказ `ruleset.versionConflict` (две вкладки админки не затирают друг друга). Строгий разбор запрещает повторяющиеся ключи; сообщения об ошибках без имён .NET-типов. `roll.lastDaysLengthFilter.enabled` — нереализованная механика (включить нельзя) до задачи C5. Эталон формата 1 заморожен в `src/GameEvent.Engine.Tests/Rulesets/Baselines/ruleset.format1.json`: его не правят, новый формат — новый файл.

### Сезон и игроки (C2)

- **D-87. Жизненный цикл сезона.** `CreateSeason(Id, Name, Ruleset, Deadline?)` создаёт черновик; `ChangeSeasonStatus` двигает только на следующий шаг (черновик → идёт → закрытие → завершён → архив), иначе `season.invalidTransition`. Игровые действия (ролл, старт, завершение) — только в «идёт» (`season.notActive`). Дедлайн задаётся при создании или командой `SetSeasonDeadline` (null убирает); в «завершён» и «архив» — `season.closed`. Автоматический переход в «закрытие» по дедлайну, запрет бросков и приём пруфов — C10.
- **D-88. Игроки и ресурсы.** У игрока очки и монетки — поля, прочие ресурсы — словарь `ResourceBag` (нулевые значения не хранятся), флаг неактивности. Игрок добавляется в «черновик» и «идёт» (дальше `season.closed`). Все входят на старт, а стартовая клетка, очки и монетки, заданные админом (SE4), — отдельные события с причинами `StartingCell`/`StartingBalance`: очки и монетки всегда равны сумме изменений (инвариант 2). Нулевые изменения не пишутся. Флаг неактивности ставит и снимает админ (`player.nothingToChange`, если значение то же; после «завершён» — `season.closed`); подсказка «без действий N дней» — чтение в админке (E2). Отход от D-21: поля `season.newPlayerDefaults` в конфиге нет — значения по умолчанию (старт, 0, 0) у команды, а форма админки (E2) показывает их заполненными, админ меняет. Отдельная настройка появится, если понадобятся другие умолчания. Имя сезона — 1–100 символов (`season.invalidName`); дедлайн хранится в UTC, установка того же значения — `season.nothingToChange`.
- **D-89. Правка игрока админом** (`AdjustPlayer`, уточняет D-21): клетка (перенос, путь из одной клетки, без шагов), дельты очков, монеток и ресурсов, сброс предложенной игры (Rolling → Idle, игра снова свободна). Каждое изменение — своё событие с причиной `AdminAdjustment`, плюс одно `PlayerAdjusted` с обязательным комментарием для публичного лога (`player.commentRequired`, код предложен `test-author`, отличается от «нечего менять»). Ничего не меняется — `player.nothingToChange`. Очки и монетки могут уйти в минус. Игрока в `Playing` так не сбросить (`player.busy`) — это дроп или тех-реролл (C6). Правка разрешена до «завершён»: в «закрытии» ещё проверяют пруфы. Команды админа идут через ту же очередь; эндпоинты админки — E2. Имена ресурсов непустые, без повторов в одной правке и не `points`/`coins` (`player.invalidResource`); список известных ресурсов в конфиге — с экономикой (этап 4). Защитные потолки (как D-86): изменение и стартовый баланс не больше ±1 000 000, комментарий до 500 символов. Перенос админом (и стартовая клетка) — не шаги: `Steps = 0`, путь из одной клетки, клетку не активирует; для истории пути (C3) он начинает новый отрезок, как телепорт. Перенос на финиш запрещён (`map.transferToFinish`): финиш — игровое событие с местами и бонусами (C9), а не правка; перенос финишировавших решит C9.

- **D-90. Путь игрока и движение назад** (C3, 2026-09-24). Путь — `PlayerPath`: список отрезков `PathSegment`, каждый — клетки, пройденные подряд по стрелкам. Перенос (`PlayerMoved.Steps = 0`: стартовая клетка, правка админом, позже телепорт) начинает новый отрезок. `Steps` со знаком: меньше нуля — движение назад. Назад идём по последнему отрезку (снимаем клетки с конца); когда в нём одна клетка, идём по основному входящему ребру (`IsPrimaryBackward`, при единственном входящем ребре — по нему), и отрезок начинается заново с достигнутой клетки. Через границу отрезка назад не ходим: перенос — не ребро (SPEC: «если отрезок кончился — основное входящее ребро»). На старте движение назад останавливается, недостающие шаги теряются. В проекции путь хранится JSON-полем `SeasonPlayer.PathJson`, а не таблицей `PathStep` из модели данных SPEC: по нему не фильтруют и не сортируют (инвариант 9), он целиком восстанавливается из лога, и одна строка на игрока проще. Точки срабатывания (`Movement.Visits`): на каждой вошедшей клетке `MoveStep`, затем `Pass` или `Stop` для последней; у переноса их нет, а ход, не вошедший ни в одну клетку (упёрся в финиш или старт), события не пишет (D-47), поэтому путь в `PlayerMoved` никогда не пуст; `Visits` на пустой путь возвращает пустой список лишь для надёжности. Подписчиков на этапе 1 нет, диспетчер — C11. Движение назад даёт те же `Pass` и `Stop`, что и вперёд: SPEC не различает направление, клетка «при проходе» срабатывает в обе стороны. Направление подписчик берёт из знака `PlayerMoved.Steps`; развилка просит выбрать ветку только при движении вперёд — это её условие (этап 2). Клетка остановки получает `MoveStep` и `Stop`, но не `Pass`: эффект, который должен сработать и при проходе, и при остановке (чекпоинт), подписывается на `moveStep`. Если у клетки нет основного входящего ребра, а входящих несколько, движение назад останавливается на ней (оставшиеся шаги теряются); на линейной карте такого не бывает, для графа это закрывает проверка редактора (этап 2), и тогда же нужен тест. **Нужно решение** (схема данных): путь в проекции — JSON-поле вместо таблицы `PathStep` из «Модели данных» SPEC. Это легко отменить: проекция целиком восстанавливается из лога, миграция до первого релиза свободна (D-73). До ответа заказчика иду с JSON-полем.
- **D-91. Машина состояний хода и ожидание выбора** (C4, 2026-09-24). Фазы остаются `Idle`, `Rolling`, `Playing` (K-5); таблица «команда хода → нужная фаза» — одна, в `TurnRules`, и все команды хода проверяются ею в одном порядке: сезон идёт → игрок известен → нет ожидания выбора (кроме `MakeChoice`) → фаза. Лимит активных прохождений держат фаза (прохождение начинается только из `Rolling`, а у играющего фаза `Playing`) и `RulesetSupport`, который пока не пускает `maxActiveRunsPerPlayer` > 1: несколько прохождений сразу требуют хода на каждое прохождение, SPEC держит одно, лимит лежит в конфиге на потом (уточняет D-53). Отдельной проверки и кода отказа для лимита нет — при лимите 1 она недостижима. Ожидание выбора — `SeasonPlayer.Choice` (`PendingChoice`: id, вид, варианты), по одному на игрока; в проекции — JSON-поле `ChoiceJson` (как путь в D-90, тот же вопрос «нужно решение» про таблицу `PendingChoice` из SPEC). Первый и пока единственный вид — выбор игры: `choiceCount` > 1 перенесён из C5 в C4, потому что без него ожиданию выбора нечем наполниться и его нельзя проверить сквозь движок. Ролл с `choiceCount` = N тянет без возврата до N доступных игр одной категории (промахи в логе, D-46) и пишет `GameChoiceRolled`; все варианты зарезервированы (D-06). Если нашлась одна игра — обычный `GameRolled`, при N = 1 лог не меняется. `MakeChoice` сразу начинает выбранную игру, как на диаграмме хода SPEC (`Choosing --> Playing`): события `ChoiceMade` и `RunStarted` в одной команде, остальные варианты освобождаются. Поэтому реролл (C6) выбранной из нескольких игры невозможен — после выбора игрок уже играет; «Уже проходил» (C5) для вариантов выбора решается в C5. Верхняя граница `choiceCount` — 20 (проверка конфига, как потолки D-86). Админский «сброс предложенной игры» (D-89) сбрасывает и ожидание выбора (`ChoiceDiscarded`). Срока жизни у предложенной игры и ожидания выбора нет: SPEC его не задаёт, снять зависшее может админ (D-89) — пункт из аудита C1 закрыт.
- **D-92. Ролл: «Уже проходил», исключения, фильтры, здоровье пула** (C5, 2026-09-24). «Уже проходил» — команда `DeclareAlreadyPlayed(PlayerId, GameId)` в фазе `Rolling` на предложенную игру или на любой вариант ожидающего выбора (ожидание выбора её не блокирует). Одна команда пишет `GameExcluded(AlreadyPlayed)` — предложение или выбор снимаются, игрок в `Idle` — и сразу новый бесплатный ролл (`GameRolled` или `GameChoiceRolled`, D-07: не реролл и ничего не тратит). Выбор из нескольких игр роллится заново целиком — на совести игрока, видно в логе (D-08). Если после исключения доступных игр нет, команда принимается только с исключением, игрок остаётся в `Idle`, следующий ролл получит отказ `roll.noAvailableGames`. Исключения — `SeasonPlayer.Exclusions` (по одному на игру, по порядку id игры), в проекции — таблица `PlayerGameExclusion` из модели данных SPEC (игрок сезона, игра, причина). Своё исключение для игрока скрыто (`Hidden`), для других игр ничего не меняет. Причины дропа и тех-реролла добавит C6. Фильтры ролла — предикаты `RollFilter` с приоритетом эффект > зона > обычный; `RollFilters.Apply` применяет их сверху вниз. Более низкий фильтр, пересечение с которым пусто, пропускается (SPEC: «пересекаются в пустоту — срабатывает более приоритетный»). Самый приоритетный из заданных фильтров сам по себе не снимается, кроме фильтра зоны (SPEC «Пустой пул»: снимается только фильтр зоны): если под ним нет игр, ролл пуст → отказ `roll.noAvailableGames` и сигнал админу. Спецролл без подходящих игр не превращается молча в обычный. «Игра считается» только если она доступна и лежит в категории колеса (вес > 0). Проверка «у игрока есть что выкинуть» одна — `Rolling.CanRoll` — и её используют и ролл, и сигнал админу, с теми же фильтрами. На этапе 1 боевых фильтров нет (`lastDaysLengthFilter` не поддержан, зоны — этап 2): ролл получает пустой список, механизм проверяется тестовыми фильтрами через внутренний `Rolling.Draw`. Сигнал админу о пустом пуле вычисляется, а не пишется в лог: `PoolStats.PlayersWithoutGames` — активные (не помеченные неактивными) игроки идущего сезона в фазе `Idle`, чей ролл сейчас ничего не найдёт (у играющего или ждущего старта игра есть; его сигнал появится, когда он вернётся в `Idle`); `PoolStats.Categories` — доступные игры по категориям без учёта личных исключений (SPEC: «в админке у каждой категории видно, сколько в ней доступных игр»). Отказ ролла событий не пишет, как и раньше. Эндпоинт статистики пула пересобирает сезон из лога на каждый запрос (как проверка целостности): только для админа, с ограничением частоты на пользователя; перейти на кэш очереди — D2. Исключение одной игры дважды невозможно (исключённая скрыта); свёртка это проверяет и падает. Снятие предложения или выбора при «Уже проходил» выводится из `GameExcluded` без отдельного события — откат (C12) восстанавливает их обратным событием для `GameExcluded`. Для C6: новый бесплатный ролл после «Уже проходил» даёт свои бесплатные рероллы (D-07) — это осознанно, цена — навсегда потерянная игра. Для C10: `DeclareAlreadyPlayed` роллит, поэтому после дедлайна запрещён так же, как ролл.
- **D-93. Реролл** (C6a, 2026-09-25). Команда `Reroll(PlayerId)` в фазе `Rolling` — на предложенную игру или на весь ожидающий выбор (ожидание выбора её не блокирует; выбор отдаётся целиком). Оплата по D-07 строго по порядку: бесплатный за этот ролл (`roll.freeRerollsPerRoll`, счётчик `SeasonPlayer.RerollsThisRoll`), затем купон реролла — ресурс `freeRerolls` (`ResourceChanged(-1, Reroll)`; порядок буквальный, купон тратится и при нулевой цене), затем `roll.rerollCost`: монетки (`CoinsChanged(-amount, Reroll)`; не хватает — отказ `roll.notEnoughCoins`, монетки в минус не уходят) или плохой ивент (`ManualEffectCreated(Bad, PaidReroll)`). Одна команда: `GameRerolled(игры, оплата)` → событие оплаты → новый ролл (`GameRolled` или `GameChoiceRolled`); новый ролл не предлагает только что отданные игры. Если кроме них ничего нет — отказ `roll.noAvailableGames`, ничего не тратится; эта проверка идёт раньше оплаты (монетки не помогут, если выкидывать нечего), потом `roll.notEnoughCoins`. Цену следующего реролла считает одна функция `RerollPrice.Next` — и команда, и экран: игрок видит её на кнопке («бесплатно», «купон реролла», N монеток, плохой ивент), платный реролл подтверждает. Ожидающие ручные эффекты игрок видит в своём ходе (`me.manualEffects`) до C11, где появится их разрешение. Счётчик `RerollsThisRoll` растёт с каждым рероллом и обнуляется, когда игрок выходит из `Rolling` (начал игру, сброс админом, «Уже проходил» без новой игры) — инвариант «не в `Rolling` ⇒ 0». Новый ролл после «Уже проходил» и после тех-реролла — это новый ролл со своими бесплатными рероллами (D-07, D-92): счётчик обнуляется и там. Ручной эффект на этапе 1 — минимум из C11: `PendingManualEffect` (id, игрок, какой ивент разыграть, источник, прохождение) в состоянии сезона и в таблице `PendingManualEffect`; разрешение («применено» / «не применимо») и базовое действие `drawEvent` — C11, тогда же создание перейдёт на `drawEvent` без изменения формата события. Тех-реролл и дроп — C6b.
- **D-94. Тех-реролл и дроп** (C6b, 2026-09-25). Дроп — `DropRun(PlayerId)` в `Playing` в любой момент (D-09): `RunDropped(штрафные кубики по отдельности)`, затем `PointsChanged(-сумма, DropPenalty)` при `drop.affectsPoints` (очки могут уйти в минус), `PlayerMoved(-сумма, DropPenalty)` назад по пройденному пути при `drop.affectsPosition` (`Movement.Backward`, не дальше старта; упёрся — события нет, D-47), `GameExcluded(Dropped)`, `ManualEffectCreated(Bad, Drop)` при `drop.mandatoryEvent = bad`. Игрок в `Idle`, монеток нет. Штраф для финишировавших (D-09) — C9. Тех-реролл — `TechReroll(PlayerId, Reason, Comment, ByAdmin)` в `Playing`: игрок — только пока с ролла (`RunState.RolledAt`) прошло не больше `roll.techRerollWindowHours`, иначе `run.techRerollWindowClosed`; админ — в любое время, флаг `ByAdmin` ставит только админский эндпоинт, отметка остаётся в логе. Причина `Other` требует комментарий (`run.reasonCommentRequired`), комментарий до 500 символов. События: `RunTechRerolled`, `GameExcluded(TechRerolled)`, затем сразу новый ролл (SPEC: `Playing --> Rolling`) со своими бесплатными рероллами; нечего выкинуть — игрок в `Idle`. Превращение в дроп — `ConvertTechRerollToDrop(RunId, Comment)` от админа, пока сезон не завершён (`Active` или `Closing`): `TechRerollConvertedToDrop(штрафные кубики)` меняет статус прохождения на `Dropped` и причину исключения на `Dropped`, дальше те же штрафные события, что у дропа, по текущим очкам и позиции; ход игрока не трогается. Дропнутая и тех-рерольнутая игра доступна другим (прохождение не `Playing`), своя — скрыта исключением. **Уточнения после ревью (2026-09-25).** (1) Окно тех-реролла «касается прохождения» (SPEC «Снапшот»), поэтому фиксируется при ролле: `RunSnapshot.TechRerollWindowHours`; правка конфига посреди прохождения окно не меняет. Штраф дропа — правило действия, а не прохождения: берётся из текущего конфига на момент дропа или превращения (так и было). (2) Тех-реролл от админа (`ByAdmin`) требует комментарий, как любая правка админа (D-89): пустой — `player.commentRequired`. (3) `TechRerollConvertedToDrop` хранит своё время `ConvertedAt`, как `RunDropped` и `RunTechRerolled`. (4) Лимит комментария один — `Kernel.Limits.MaxCommentLength` (500), им пользуются движок и API. (5) Экран не угадывает правила: в своём ходе игрок получает штраф дропа (`me.dropPenalty`: кубики, что отнимает, будет ли плохой ивент) и текст подтверждения собирается из него; подсказку «рано дропать» решает сервер по своим часам (`me.dropHintMinutes` не пуст, только пока сыграно меньше `minPlayMinutesBeforeDrop`); открыто ли окно тех-реролла — тоже сервер (`me.techRerollOpen`), после окна кнопки нет, игроку сказано обратиться к админу. (6) Пометка SPEC «Игру дропнул или техдропнул другой — пометка с причиной»: у предложенной игры и у вариантов выбора есть `marks` — кто из других игроков в этом сезоне её дропнул или тех-рерольнул; причина пометки — дроп или тех-реролл (подробная причина тех-реролла есть в логе). (7) Штраф дропа для финишировавших (D-09: не первым — только очки, замороженному первому — ничего; то же для превращения тех-реролла в дроп) — задача C9, строка в матрице.
- **D-95. Повтор команды сверяется по телу** (2026-09-25, по трём ревью C5–C6). Повтор с тем же `CommandId` считается дублем, только если совпадают сезон, тип команды, автор **и тело команды**: у каждого события в логе есть `CommandHash` — SHA-256 JSON команды (`EngineJson`). Иначе — отказ `command.idReused`, а не тихий ответ событиями первой команды (раньше админ, повторно использовавший id с другим игроком или прохождением, получал «успех», а действие не выполнялось). Отклонённые команды в лог не пишутся, поэтому их id можно использовать снова. Сравнение действует в пределах одной версии приложения: повтор, попавший на деплой, который поменял форму команды или правил, получит `command.idReused` — это безопасно (двойного выполнения нет), клиент делает новый id на каждое действие. Команда, которую нельзя сериализовать (null в ненулевом поле), отклоняется с `command.invalid`, а не падает.
- **D-96. Завершение: челлендж, часы, монетки, хороший ивент, отзыв** (C7a, 2026-09-25). В снапшот при ролле добавлены `ChallengeExtraDice` (`reward.challengeBonus.extraDice`) и `Coins` (`reward.coins`): это награда за прохождение (SPEC «Снапшот»). `CompleteRun` несёт `ChallengeDone`: столько же дополнительных кубиков того же типа (по сложности), бросаются отдельно и хранятся отдельно (`CompletionRolled.ChallengeDice`, D-14: правка часов их не трогает); очки и шаги — сумма всех кубиков. Проверка челленджа — вместе с пруфом (D-13, C8). Если в снапшоте нет часов, оценка игрока требует источник (`HoursSource`: ссылка или короткая пометка, до 300 символов) — иначе `run.hoursSourceRequired`; если часы в снапшоте есть, оценка и источник игнорируются. Монетки за прохождение (Q-2) — `max(coins.min, ⌊часы × coins.perHour⌋)` по засчитанным часам, `CoinsChanged(+, CompletionReward, RunId)`. Сложность с `grantEvent` («выше сложной» → хороший) создаёт ручной эффект `ManualEffectCreated(Good, Difficulty, RunId)` (D-10). Отзыв — оценка 1–10 и необязательный текст до 2000 символов (пустой → нет текста): в `CompleteRun.Review` или позже командой `ReviewRun` на своё завершённое прохождение (новый отзыв заменяет прежний); событие `RunReviewed`, состояние `RunState.Review`, таблица `Review` (модель данных SPEC). Отзыв можно оставить, пока сезон не в архиве. Порядок событий завершения: `RunCompleted`, `CompletionRolled`, `PointsChanged`, `PlayerMoved`, `CoinsChanged`, `ManualEffectCreated`, события финиша (D-99), `RunReviewed`. Условия ивентов (`unmetConditionPolicy`) — этап 5. **Уточнения после ревью (2026-09-25).** (1) Челлендж — «из заметки к игре», а заметки в пуле пока нет (G1, F1), и проверка с пруфом — C8. Поэтому заявка челленджа закрыта флагом `features.challenges` (по умолчанию выключен; поле необязательное, старые конфиги читаются): при выключенном флаге галочки в форме нет, движок отклоняет `ChallengeDone` кодом `feature.disabled`. Включать — когда у игры будет заметка-челлендж и проверка с пруфом. Вариант награды «хороший ивент» вместо кубика (SPEC: «например») на этапе 1 не поддержан — только `extraDice`; появится с ивентами (этап 5). (2) Монетки считаются по засчитанным часам, но не больше потолка кубиков: `min(часы, diceCount.max × hoursPerDie)` — иначе оценка игрока в 1000 ч даёт 1000 монеток. Правка часов админом (C7b) пересчитывает и монетки; смена сложности (Q-5) пересчитывает и кубики челленджа. (3) У `reward.coins.perHour` и `min` есть потолки проверки конфига (как D-86), чтобы опечатка не ломала каждое завершение. (4) Слишком длинный источник оценки — свой код `run.hoursSourceTooLong`; текст отзыва обрезается по краям на сервере, пустой — нет текста. (5) Отзыв позже — только API; кнопка на экране — H (строка W9).
- **D-97. Правка часов и смена сложности завершённого прохождения** (C7b, 2026-09-25). Обе — команды админа с обязательным комментарием (до 500), только для завершённого прохождения (`run.notCompleted`), пока сезон не завершён (`Active` или `Closing`; иначе `season.closed`); то же значение, что было, — `run.nothingToChange`. **Часы** (`CorrectRunHours`, часы > 0): число кубиков по новым часам и правилу из снапшота (D-13); недостающие кубики бросаются и добавляются в конец, лишние снимаются с конца (D-14); кубики челленджа не трогаются. Событие `RunHoursCorrected(было, стало, добавленные, сколько снято)`, затем разница: `PointsChanged(±, RunCorrection)`, `PlayerMoved(±, RunCorrection)` — вперёд по стрелкам или назад по пройденному пути от текущей клетки (не дальше старта; упёрся — события нет), `CoinsChanged(±, RunCorrection)` — монетки пересчитываются по новым часам (D-96, с потолком). **Сложность** (`ChangeRunDifficulty`): каждый кубик, и кубики челленджа тоже, становится `⌈старое × новые грани / старые грани⌉` (Q-5); событие `RunDifficultyChanged` хранит «было/стало» каждого кубика; затем разница очков и шагов. Ивент сложности: если у прежней сложности был `grantEvent` и его ручной эффект ещё ждёт — `ManualEffectResolved(NotApplicable, комментарий)`; если уже разыгран — остаётся, админ правит вручную; если у новой сложности есть `grantEvent` — новый ручной эффект. `ManualEffectResolved(эффект, игрок, прохождение, исход, комментарий)` — минимум из C11: разрешённый эффект уходит из списка ожидающих (и из таблицы `PendingManualEffect`); команды игрока и админа для разрешения — C11. `RunHoursCorrected` хранит значения снятых кубиков, а не только их число. Неизвестная сложность в команде — отказ `command.invalid`. Сценарий «ивент выше сложной уже разыгран → сложность понижена → снова повышена» даёт второй хороший ивент для того же прохождения: принимается, админ правит вручную (Q-5). Правила для финишировавших (правка не сдвигает зафиксированную позицию и не начисляет замороженному) — C9, строка RR8 в матрице.
- **D-98. Пруфы** (C8, 2026-09-25). Пруф — у завершённого прохождения, одно состояние на прохождение (`RunState.Proof`): статус «ждёт» / «одобрен» / «отклонён», ссылки (до 5, только `http`/`https`, до 500 символов каждая), заметка (до 500), свидетель — другой игрок сезона, видевший прохождение (SPEC: «прохождение видел другой участник»). Файлы на этапе 1 — ссылками (загрузка файлов и галерея — позже); таблица `Proof` (модель данных SPEC). **Игрок** `SubmitProof(PlayerId, RunId, Links, Note, WitnessId)`: своё завершённое прохождение, нужен хотя бы один из: ссылка или свидетель; пока пруф не проверен — новая отправка заменяет прежнюю; проверенный пруф не меняется (`proof.alreadyReviewed`). Пруф можно слать и после дедлайна (SPEC), пока сезон не завершён. **Админ** `ApproveProof(RunId, Difficulty?, Comment?)` — одобрить (с отправленным пруфом) или «одобрить без скрина» (пруфа нет; комментарий обязателен). `Difficulty` — сложность по пруфу: если ниже заявленной, в той же команде пишется смена сложности по Q-5 (`RunDifficultyChanged` и разница, D-97); выше заявленной по пруфу не поднимают (`proof.difficultyAboveClaimed`). `RejectProof(RunId, Comment)` — реджект (D-15): прохождение получает статус `Rejected`; снимаются очки, которые дало это прохождение, с учётом правок (сумма его кубиков, в том числе челленджа), и клетки, которые оно действительно прошло (`RunState.Moved` — пройденные клетки, а не выпавшие шаги: шаги, сгоревшие на финише, клеток не давали, D-47), назад по пройденному пути от текущей клетки, не дальше старта; монетки за прохождение тоже снимаются (это та же награда за прохождение, иначе ложное завершение выгодно; отступление от буквы SPEC «снимаются очки и клетки», **нужно решение** заказчика — до ответа снимаем); ожидающий ручной эффект сложности этого прохождения — «не применимо»; игра снова не пройдена в сезоне и доступна всем, включая этого игрока. Реджект финиша и места — C9. **Очередь пруфов** — `ProofReviewOrder.Order`: ждущие проверки; прохождения, которые довели игрока до финиша, — сверху (SPEC), дальше по времени завершения; админский `GET /api/admin/seasons/{id}/proofs`. Правки часов и сложности (C7b) остаются доступны админу и после одобрения (исправление ошибок); отклонённое прохождение не правится (`run.notCompleted`), вернуть его можно только откатом (C12). Одобрить или отклонить можно одно завершённое непроверенное прохождение; повторная проверка — `proof.alreadyReviewed`. Пруф, проверка и реджект — пока сезон не завершён (`Active` или `Closing`). **Уточнения после ревью (2026-09-25).** (1) Правка часов (C7b) при уменьшении тоже снимает только реально пройденные клетки сверх новой суммы кубиков. (2) Флаг «довёл до финиша» (`ReachedFinish`) следует за последним ходом этого прохождения: правка, уводящая с финиша, его снимает. (3) Одобрение с понижением сложности требует комментарий, как одобрение без скрина; текста по умолчанию в движке нет (инвариант 13). (4) Ссылки и заметка пруфа хранятся обрезанными, пустая заметка — нет заметки. (5) На экране пруф можно отправить к последнему завершённому прохождению, со свидетелем из игроков сезона; пруф к более раннему прохождению — через API, в интерфейсе — H. (6) Проверка челленджа с пруфом (D-13) — когда будет включён флаг `features.challenges` (нужна заметка-челлендж в пуле, E1/F1); пока флаг выключен, кубиков челленджа нет.
- **D-99. Финиш, первое место, бонусы и заморозка** (C9a, 2026-09-25; по Q-3, Q-4 и поправке к заморозке). Когда ход прохождения приводит фишку на финиш, та же команда пишет `PlayerFinished(игрок, прохождение, порядок, время, запас)`; порядок — номер среди финишировавших (1, 2, 3…), номера не переиспользуются. `FinishState` хранит порядок, прохождение финиша, время, заморозку, текущий бонус (у игрока не больше одного бонуса финиша, Q-4) и **запас** — шаги, сгоревшие на финише при финишном ходе. **Первый** — стоящий финиш с наименьшим номером. **Бонусы (Q-4)**: у стоящих финишировавших, упорядоченных по номеру, первый получает 0, второй — `finish.bonusByOrder[0]`, третий — `[1]`…, дальше `bonusAfterList` (`FinishLine.Bonus(правила, место)`); при любом изменении состава финишировавших бонусы всех пересчитываются по новому порядку разницей (`PointsChanged(±, FinishBonus / FinishBonusRevoked)`), итог в логе; замороженному не пересчитывается (у первого бонус 0). **Позиция финишировавшего (Q-3)** складывается только из прохождений до финиша включительно: прохождения после финиша, штраф дропа и правки после финиша фишку не двигают. Реджект или уменьшение (часы, сложность) прохождения до финиша на k: если k ≤ запаса — запас уменьшается (`FinishSurplusChanged`), финиш остаётся; иначе финиш отзывается (`PlayerFinishRevoked`), фишка отходит на k − запас клеток назад по пройденному пути, бонус снимается, бонусы остальных пересчитываются. Увеличение такого прохождения добавляет к запасу. **Предварительный первый**: очки и монетки как обычно, на других не влияет, его прохождения после финиша не делают игру «пройденной в сезоне» (D-16). **Заморозка** (`PlayerFrozen`): первое место окончательное, когда одобрены пруфы всех его прохождений до финиша включительно (Q-3) — тогда же заморозка; эти прохождения поднимаются в начало очереди пруфов; при `finish.requireApprovalForFirst = false` — сразу при финише первым; ставший первым после отзыва чужого финиша замораживается сразу, если все его прохождения до финиша уже одобрены. **Замороженному ничего не начисляется и ничего не снимается** (поправка к заморозке, Q-3): завершение пишет кубы без очков, монеток, движения и ивента сложности; дроп и превращение в дроп — без штрафа и без плохого ивента; правки — без очков и монеток; реджект его прохождений после финиша ничего не снимает; рероллы в свободном режиме бесплатны. Правка, которая довела бы нефинишировавшего до финиша, останавливает фишку на клетку раньше: финиш даёт только прохождение (RR8). Лидерборд, места и тайбрейк — C9b. Реджект прохождения замороженного ничего не снимает, но ожидающий ивент сложности этого прохождения становится «не применимо» (D-98). Место замороженного первого окончательное: правка его прохождений (до или после финиша) не меняет ни очков, ни запаса, ни позиции и не отзывает финиш. Реджект или правка, отзывающие финиш, пишут движение назад с причиной самой команды (`ProofRejected` или `RunCorrection`). Очередь пруфов: сверху прохождения стоящих финишировавших до их финиша включительно (`decidesFinish` в API); после отзыва финиша они уходят из верха. **Уточнения после ревью C9a** (2026-09-25): (1) признаки «после финиша» и «свободный режим» решаются при завершении и хранятся в `RunCompleted` (`afterFinish`, `freeMode`), при повторе не пересчитываются; (2) при отзыве финиша прохождения после него снова обычные (`AfterFinish = false`), свободный режим остаётся (D-16); (3) игра, пройденная первым в свободном режиме, для остальных доступна, а для него самого — пройдена в сезоне; (4) уменьшение финишного прохождения берёт разницу кубов (сгоревшие шаги лежат в запасе), а более раннего — только клетки, пройденные сверх нового числа кубов (при реджекте — все пройденные им клетки); (5) события финиша пишутся после монеток и ивента сложности прохождения, но до отзыва — заморозка наступает после наград; (6) бонусы при каждом пересчёте берутся из текущих правил сезона; (7) смена сложности у замороженного закрывает ожидающий ивент старой сложности, новый не создаётся; (8) админ не переносит финишировавшего на другую клетку (`player.finished`): его позиция меняется только через прохождения; (9) API: у замороженного следующий реролл бесплатен (`freeMode`), штрафа дропа нет, у остальных финишировавших штраф дропа не двигает фишку. (10) При `finish.requireApprovalForFirst = false` первый заморожен сразу, и реджект его финишного прохождения потом ничего не снимает и финиш не отзывает: сезон сам отказался от проверки финиша, место окончательное (как у любого замороженного); сам пруф помечается отклонённым. (11) Перенос админом с указанием текущей клетки — не перенос, проверок клетки нет.
- **D-100. Лидерборд, места и тайбрейк** (C9b, 2026-09-25). Место 1 — стоящий финиш с наименьшим порядком (первый; «предварительно», пока не заморожен), независимо от очков. Остальные, включая других финишировавших и неактивных, — по очкам (больше — выше), затем тайбрейки из `ranking.tiebreakers` по порядку: `completedRuns` — число завершённых и не отклонённых прохождений (больше — выше); `earliestFinalScore` — кто раньше набрал текущие очки. «Раньше» считается не по часам, а по номеру изменения очков в сезоне: каждое ненулевое `PointsChanged` получает следующий номер (`SeasonState.PointsChanges`), игрок хранит номер своего последнего (`SeasonPlayer.PointsTick`, 0 — очки не менялись); меньше — раньше. Номер выводится свёрткой лога, формат событий не меняется, повтор детерминирован. Полная ничья — общее место, следующее пропускается (1, 2, 2, 4); внутри ничьей строки по id игрока. «Клеток до финиша» — наименьшее число шагов вперёд по рёбрам карты до клетки-финиша (0 на финише, нет пути — пусто). Лидерборд живой: «на момент дедлайна» даёт C10, потому что после дедлайна очки меняют только пруфы и правки админа. Ранжирование — чистая функция движка `Leaderboard.Rank` над записями (`RankingEntry`), чтобы API строил лидерборд из проекции без повтора лога, а движок и инвариант 10 — из состояния. Номер берётся у последнего ненулевого изменения очков, поэтому реджект и пересчёт бонуса сдвигают игрока «позже» — это принято: итоговые очки он набрал именно тогда. Откат команды (C12) — исключение: компенсирующие события отката возвращают игроку прежний `PointsTick`, будто отменённой команды не было. Представление сезона читает проекцию несколькими запросами без общей транзакции (архитектурный тест запрещает Web открывать транзакции): если между запросами закоммитится команда, одна выдача может смешать очки до неё и прохождения после; следующее обновление через хаб это исправляет. Принято для этапа 1; если понадобится строгость — чтение снимком в Infrastructure (D8). Число засчитанных прохождений считается запросом `GROUP BY` по прохождениям сезона, а не колонкой: на 16 игроков и сотни прохождений это дёшево; колонка — если профилирование на демо-сезоне (F) покажет нужду.
- **D-101. Жизненный цикл сезона: дедлайн, закрытие, итоги** (C10, 2026-09-25). **Дедлайн по часам движка**: как только `IClock` ≥ дедлайна, ходовые команды игрока (ролл, «уже проходил», реролл, выбор, старт, завершение, дроп, тех-реролл, в том числе тех-реролл админом от имени игрока) отклоняются `season.deadlinePassed`, даже если статус ещё «идёт»: планировщик может опоздать, а «засчитывается бросок, сделанный до дедлайна» (инвариант 11, K-7). Завершение после дедлайна не засчитывается: прохождение остаётся «играется» и в итоги не идёт. Правки админа (часы, сложность, превращение тех-реролла в дроп, правка игрока), пруфы, одобрение, реджект и отзывы после дедлайна разрешены (K-7). **Закрытие**: планировщик в Infrastructure раз в `Scheduler:IntervalSeconds` (по умолчанию 30) находит сезоны «идёт» с наступившим дедлайном и шлёт через общую очередь системную команду `ReachDeadline` (автор — система, `CommandId` выводится из сезона и дедлайна, поэтому повтор — дубликат). Движок принимает её только в статусе «идёт» и только когда дедлайн наступил по его часам: `SeasonStatusChanged(Active → Closing)`. Админ может закрыть раньше обычным переходом статуса. Дедлайн меняется только в статусах «черновик» и «идёт» (в «закрытии» и позже — `season.closed`). **Завершение** (`Closing → Finished`) только когда очередь пруфов пуста — все завершённые прохождения одобрены или отклонены (`season.proofsPending`, SPEC «Итоги только после проверки всех пруфов»); та же команда пишет `SeasonResultRecorded` — снимок лидерборда (D-100) в этот момент; «на момент дедлайна» — потому что после дедлайна очки меняют только пруфы и правки прохождений до дедлайна. После завершения лидерборд берётся из снимка. **Архив** — следующий переход, ничего не меняет. API админа: `POST /api/admin/seasons/{id}/status` и `/deadline`; в представлении сезона — статус и дедлайн (показывается по Москве с подписью). Старые тесты, которые доводили сезон до «завершён» с непроверенными пруфами, чтобы проверить запрет действий после итогов, получают это состояние напрямую из подготовленного лога событий (движок такой переход больше не примет); проверяемое правило не меняется. Тест порядка статусов ожидает при завершении два события: смену статуса и итоги; подделка завершения — только через явный хелпер `Scenario.MoveStatusToForcingFinish`, обычный `MoveStatusTo` требует, чтобы каждый переход был принят. **После ревью C10**: дедлайн должен быть в будущем (`season.deadlineInPast`) — опечатка в годе иначе закрыла бы ходы и сезон без возможности вернуть; снять дедлайн можно всегда в «черновике» и «идёт»; черновик с прошедшим дедлайном не запускается. Ручная правка очков админом (`AdjustPlayer`) в «закрытии» разрешена и попадает в итоги наравне с правками прохождений: админ исправляет итог сезона до объявления (K-7). Планировщик опрашивает раз в 5 с (`Scheduler:IntervalSeconds`, > 0, проверяется при старте), `Scheduler:Enabled=false` выключает его цикл (в тестах, где часы двигают вручную); упавший проход не останавливает цикл. Экран прячет все ходовые действия, когда сезон не «идёт» или дедлайн по часам браузера прошёл, и показывает заметку «закрытие» до тика планировщика.
- **D-102. Разрешение ручных эффектов** (C11a, 2026-09-25; по D-31). Команда `ResolveManualEffect(эффект, исход, комментарий, игрок)`: игрок разрешает только свои (`effect.notYours`), админ — любые (игрок не указан, ставит админский эндпоинт). «Не применимо» всегда с комментарием; админ пишет комментарий всегда (D-89); «применено» от игрока — комментарий по желанию (пустая строка в событии). Комментарий до 500 символов. Разрешается только ожидающий эффект (`effect.notPending`, повтор той же командой — дубликат по `CommandId`). Разрешать можно в статусах «идёт» и «закрытие»; после завершения — `season.closed`. Разрешение ничего не меняет в очках и позиции: на этапе 1 ручной эффект — напоминание разыграть ивент вручную, а изменения, если они нужны, админ вносит правкой игрока (D-21). API: `POST /api/seasons/{id}/effects/{effectId}/resolve` (игрок) и `POST /api/admin/seasons/{id}/effects/{effectId}/resolve` (админ), тело `{commandId, outcome, comment}`; на экране у каждого ручного эффекта — «Применено» и «Не применимо» с полем комментария. Админ видит все ожидающие эффекты сезона: `GET /api/admin/seasons/{id}/effects` (игрок, эффект, источник, прохождение; экран — H8). Существование эффекта проверяется раньше владельца: игрок по коду отказа может узнать лишь, ожидает ли чужой случайный идентификатор (UUID v7) разрешения, — это не раскрывает ничего полезного, отдельный код не вводим. На экране кнопки разрешения видны в «идёт» и «закрытии», после завершения эффект показывается без них. Инвариант разрешения (D-97) уточнён под это правило: «не применимо» — всегда с комментарием, пустой комментарий только у «применено» от владельца, админ — всегда с комментарием. Попутно исправлена проверка «остальные меняются только пересчётом бонусов» в тестах инвариантов: она не учитывала номер изменения очков из C9b (D-100), который пересчёт бонуса законно меняет; ошибка была в тесте, движок верен (редкий случай, найден прогоном 20 000 партий).
- **D-103. Модель контента и диспетчер эффектов** (C11b, 2026-09-25; по D-24 и CONTENT.md). **Модель**: `Content/` в движке — `ObjectDefinition` (вид, название, описание, редкость, цена, окно, флаги, ручной, пруф, охват достижения, эффект), `EffectSpec` (цель, триггер, срок, условие, перехват, действия или ветвление по броску), 12 базовых действий как записи, выбранные полем `type` (инвариант 7), зона, особые клетки, голосование и челлендж недели. Значение в действии (`ContentValue`) — целое число, кубики (`NdS`, 1–20 кубиков, 2–100 граней, со знаком) или ссылка (`$имя`, со знаком); пишется обратно в том же виде. Разбор строгий, как у правил (D-23): неизвестное поле, неизвестный `type`, дробь вместо целого — ошибка с путём. Правила сверх типов — `ContentValidator` (ошибки с JSON-путём): id — слова через дефис до 50 символов; у предмета есть окно, у остальных нет; у достижения есть охват; объект без эффекта — только ручной; эффект, спецролл и достижение ждут триггера, предмет и ивент — нет; перехват только на `hostileIncoming`; у эффекта либо действия, либо ветвление; `among` только для `chosen`/`randomActive`; срок — ровно одно положительное поле; `$roll` — только после броска (в ветвлении — всегда), `$choice` — только после выбора; этапы кубиков кроме прибавки — целые числа; ветвление по кубикам покрывает каждый исход ровно одним случаем. Тонкости формата CONTENT.md не менялись. Отличие от SPEC-таблицы «ObjectDefinition»: поле «удалён» появится с таблицей определений (этап 4), сейчас контент только загружается и проверяется. JSON-схема для редактора в админке — вместе с ним (этап 4). **Диспетчер**: после принятой команды каждый обработчик `ITriggerHandler` из контекста движка реагирует на её события, затем на реакции — уровень за уровнем; события команды — уровень 0, реакции — до 3 уровней, всего не больше 50 событий на команду (`Limits.MaxEffectDepth`, `Limits.MaxEventsPerCommand` — защитные пределы из SPEC, не баланс, поэтому не в `Ruleset`). Первая реакция сверх предела обрывает цепочку событием `EffectChainCut(предел, уровень, событий до обрыва)` — оно последнее и не меняет состояние. Обработчик видит состояние со всеми событиями, записанными до него. В продукте обработчиков на этапе 1 нет (контекст без них), лимиты проверяются тестовыми эффектами (D-24). **После ревью C11b**: событие обрыва пишется сверх 50 (51-м), собственные события команды диспетчер не ограничивает — команды пишут единицы событий. Уточнения формата CONTENT.md (примеры не меняются): `stat` — одно из четырёх имён таблицы («hostileReceived», «completedStreakWithTag», «allDiceMax», «runHours»), опечатка — ошибка разбора, у каждой — обязательные параметры; условие и фильтр не пустые, `minHours` ≤ `maxHours`; цена — только у предметов; срок — только у эффектов и спецроллов; перехват — только у эффекта; результат голосования действует сразу (без триггера, срока и перехвата); `$result` — только в `onResult` голосования; у `roll` кубики без минуса; у `reroll` число ≥ 1; кубики пишутся без ведущих нулей; варианты выбора — источник или список хотя бы из двух; `null` в действиях и параметрах — ошибка. Значения, которых нет в примерах, но которые понадобятся этапам 4–6: голосуют `players` или `everyone`, проверка челленджа `auto` или `manual`, фильтр объектов для `takeObject`/`transformObject` — вид, редкость, id, враждебность. Имена: `TargetSelector`, `WeeklyChallengeDefinition` (не путать с челленджем прохождения), `ZoneDefinition`, `PollDefinition`; тип особой клетки — отдельное перечисление `ContentCellType` (магазин, ивент, телепорт, бонус очков, чекпоинт), а не `CellType` карты: клетки карты этапа 1 — старт, пустая, финиш, особые клетки появятся на карте в этапе 2 вместе с редактором.
- **D-104. Откат команды** (C12a, 2026-09-25; по SPEC «Откат действий», D-20). Админ откатывает команду целиком: `UndoCommand(команда, комментарий)` (комментарий обязателен, до 500). **Компенсация — одно событие** `CommandUndone`: всё, что команда затронула, получает значения, бывшие до неё, — игроки, прохождения и ожидающие ручные эффекты, которые она изменила; созданные ею удаляются; поля сезона (статус, дедлайн, название, правила), если она их меняла. Это то же, что её события, обращённые в обратном порядке, потому что откат разрешён, только когда ничто позже не трогало тех же сущностей, — а одно событие вместо обратного к каждому из ~40 типов не разойдётся с `Apply` при новых событиях. Событие хранит снимки сущностей в формате движка: если записи состояния изменятся, у события появится версия с преобразованием (как у всех событий, D-49). Счётчики финишей и изменений очков не откатываются: номера никогда не повторяются; номер изменения очков самого игрока возвращается к прежнему (обещано в D-100). Правила возвращаются новой версией (+1), чтобы номер версии всегда означал один набор правил. **Зависимые** (D-20): движок получает лог по командам (`EngineContext.History`, только для отката), повторяет его и для каждой команды находит затронутое — изменённых, созданных или удалённых игроков, прохождения и эффекты, игры из её событий (любые `GameId`/`GameIds`, в том числе промахи колеса и варианты выбора, найденные отражением) и игры её прохождений, поля сезона, порядок финиша (`PlayerFinished`, `PlayerFinishRevoked`, `PlayerFrozen`). Более поздняя неотменённая команда (не откат) с пересечением — зависимая: откат отказывает `undo.dependents` и называет их (`Rejection.Related`, в API — поле `related`); их откатывают по порядку или правят вручную. Не откатываются: создание сезона, сам откат (откат отката не поддерживается, действие делают заново), уже откатанная команда; после завершения сезона — ничего (`season.closed`). В логе события откатанной команды остаются и помечаются `UndoneByEventId`. Проекция умеет удалять игроков, прохождения с пруфом и отзывом, исключения, пруфы и отзывы. API админа: `POST /api/admin/seasons/{id}/undo` и список команд сезона `GET /api/admin/seasons/{id}/commands` (новые сверху: тип, автор, время, откатана ли, типы событий); экран — H. Инвариант 13: принятый откат даёт то же состояние, что лог без этой команды (с точностью до растущих счётчиков и номера версии правил). **После ревью C12a** (зависимость бывает не только по записи, но и по чтению): игроки, чьё предложение или варианты выбора держали игру, дают ключ этой игры; прохождение даёт ключ своего игрока; всё, что касается финишировавшего, его прохождений, запаса и бонусов финиша, даёт ключ порядка финиша (иначе откат одобрения оставил бы первого замороженным с непроверенным прохождением); свидетель пруфа даёт ключ своего игрока. Команда, менявшая поля сезона (статус, дедлайн, правила, название), делает зависимыми все более поздние команды: каждая решалась при этих полях. Откат не возвращает дедлайн, который уже прошёл (`season.deadlineInPast`), и не открывает сезон, дедлайн которого наступил (`season.deadlinePassed`) — поэтому закрытие планировщиком и досрочное закрытие после дедлайна не откатываются, а повтор планировщика не упирается в откатанную команду. Повтор идентификатора откатанной команды — отказ `command.undone`, а не молчаливый дубликат. Снимок сезона хранит правила, только если команда их меняла. Без истории движок отказывает `undo.noHistory`, а не падает. Случайные партии теста инварианта 13 включают пруфы, одобрение, реджект, правку часов, реролл, дедлайн, закрытие и перенос, и после каждого принятого отката проверяют правила: игру держит один игрок, в черновике нет прохождений, фаза соответствует активному прохождению, замороженный первый — с одобренными прохождениями до финиша.
- **D-105. Проверка целостности и перенос сезона** (C12b, 2026-09-25; по SPEC «Расхождение лога и состояния», «Экспорт и импорт сезона», D-32). **Проверка целостности** — только чтение: состояние из лога сравнивается с тем, что описывают таблицы проекции (`SeasonProjection.ReadAsync`), по сезону, игрокам, прохождениям и ручным эффектам — поле за полем; если лог сдвинулся между чтениями, проверка читает заново (до трёх раз). Админский эндпоинт `GET /api/admin/seasons/{id}/integrity`. **Архив** — zip с `season.json` (формат 1): лог сезона (тип, версия, данные события, команда, её тип и отпечаток, автор, время, какое событие откатило), пользователи, упомянутые в сезоне (авторы и игроки: id, логин, имя, роль — без паролей), весь пул игр и категорий. Снимок состояния не кладём, в отличие от D-32: состояние — свёртка лога, а импорт всё равно сверяет построенную проекцию. **Импорт** — инструмент `npm run season:import` (не сайт) в локальную или тестовую копию: одна транзакция; аккаунты по логину, отсутствующие — удалённые заглушки без пароля; недостающие игры и категории добавляются; события пишутся как были (старые версии читаются через преобразование и пишутся в текущей), id аккаунтов заменяются в `SeasonPlayerAdded` и в снимках игроков `CommandUndone`; проекция строится команда за командой тем же кодом, что у очереди; метки отката переносятся; при непройденной проверке целостности всё откатывается. Импорт пишет в базу мимо очереди — это единственное такое место кроме миграций и сида разработки, разрешено архитектурным тестом явно: сезон новый, ни одна команда до него не дотянется. Сезон с тем же id повторно не загружается (id игроков и прохождений глобальны в таблицах). Выгрузка: `GET /api/admin/seasons/{id}/export` (админ, лимит чтения) или `npm run season:export`. **После ревью C12b**: события копируются как хранились (тип, версия, данные) — лог не переписывается; исключение — два вида событий с id аккаунтов (`SeasonPlayerAdded`, `CommandUndone`), они пишутся заново в текущем формате с id аккаунтов этой базы. Аккаунты выгружаются все, кого называет лог (авторы, прибытия игроков, снимки в откатах); неизвестный архиву аккаунт — отказ. Заглушки — удалённые зрители (роль из архива не переносится), хеш с префиксом `imported:`, который вход считает неверным паролем, а не ошибкой. Совпавший по логину аккаунт с другой ролью — отказ, если не разрешено явно (`--allow-role-mismatch`); совпадения печатаются. Пул живой копии не меняется без просьбы: игры сезона добавляются удалёнными, категории не добавляются (D-19), `--with-pool` — живыми с категориями. Архив проверяется до записи: события 1..N, первое — создание именно этого сезона, метки отката и аккаунты разрешимы, логины и id уникальны, игры и категории корректны; `season.json` не больше 200 МБ. При отказе транзакция откатывается и контекст очищается. Проверка целостности сравнивает и историю версий правил, помечает отчёт неустоявшимся (`settled: false`), если лог двигался; открыть транзакцию чтения ей не даёт архитектурный тест, поэтому — повтор до трёх раз. Инструмент: ещё `npm run season:check`.
- **D-106. Аккаунты через очередь** (D8, 2026-09-25; уточняет D-66, D-67). Аккаунты меняются командами той же очереди (инвариант 2) — `CreateAccount`, `ResetPassword`, `ChangeOwnPassword`, `ChangeAccount` (имя, роль), `DeleteAccount`, `RestoreAccount`, для сида и тестов `SeedAccount` (известный пароль, без обязательной смены; из API недоступна). Их события — в общем логе без сезона (`GameEvent` с `SeasonId = Guid.Empty`, как пул по D-19): `account-created`, `account-password-reset`, `account-password-changed`, `account-changed`, `account-deleted`, `account-restored` — журнал, кто что сделал с аккаунтом. Пароли и их хеши в лог не попадают, поэтому **источник истины по аккаунтам — таблица `User`**, правила читают её, а лог — журнал (в отличие от сезона, где таблицы — проекция лога). **Временный пароль** (12 символов без похожих букв и цифр) делает сама очередь и отдаёт один раз в ответе (`CommandOutcome.Secret`, нигде не хранится); повтор той же командой — `duplicate: true` без пароля, нужен новый сброс; id нового аккаунта тоже даёт очередь, поэтому повтор создания — та же команда. Отпечаток команды для проверки повтора (D-95) у команд с секретом считается без секрета (`ISecretCommand`), чтобы в базе не лежал несолёный SHA-256 пароля. Очередь хеширует через интерфейс `IPasswords` из Infrastructure; реализация `Passwords` (PBKDF2 из ASP.NET Core Identity) остаётся в вебе — инфраструктура не зависит от ASP.NET Core (архитектурный тест). Правила: логин — 2–32 латинские буквы, цифры, «.», «-», «_», уникален без учёта регистра и среди удалённых; имя 1–64; пароль 8–256, не логин и не текущий; последнего неудалённого админа нельзя удалить или понизить; смена пароля, сброс, смена роли и удаление меняют метку безопасности — сессии аккаунта кончаются на следующем запросе (D-67), а его соединения хаба закрываются сразу (`HubSessions`); смена своего пароля заново выдаёт куку этой сессии. **С временным паролем** открыты только `me`, смена пароля, выход, антифорджери и вход — остальной API отвечает 403 `account.mustChangePassword`; экран сразу показывает форму смены. API админа: `GET /api/admin/accounts`, `POST /api/admin/accounts`, `POST /api/admin/accounts/{id}` (имя, роль), `.../reset-password`, `.../delete`, `.../restore`; своё: `POST /api/auth/password` (с текущим паролем, лимит попыток как у входа). Сид разработки заводит аккаунты командами; экран админки — H8. **После ревью D8**: временные пароли и метки безопасности берутся из системного криптогенератора, а не из источника случайности игры (зерно в тестовых эндпоинтах не должно их предсказывать); восстановленный аккаунт входит только после сброса — прежний пароль остаётся позади (хеш с префиксом `disabled:` не подходит ни к одному паролю, как у заглушек импорта); смена своего пароля несёт метку, при которой проверен текущий пароль, и устаревает, если аккаунт сбросили или поменяли в промежутке (`account.stale`); проверка текущего пароля ограничена как вход — по логину и адресу, неудачи в журнал; повтор запроса с секретом не подтверждается: `account.repeat` вместо «принято» (пароль в повторе мог быть другим); временный пароль закрывает и хаб. Аккаунты тестов (`SiteFactory`) и заглушки импорта (D-105) пишутся мимо очереди — у них нет `account-created` в общем логе: журнал аккаунтов полон только для созданных через очередь.
- **D-107. Наблюдаемость** (D7, 2026-09-25; по SPEC «Наблюдаемость»). **Логи**: Serilog — консоль и файл `var/logs/game-event-YYYYMMDD.log` (путь `Logging:File:Path` от корня контента, `Logging:File:Enabled`), файл в день и не больше 20 МБ, хранятся последние 30; уровни — из `Logging:LogLevel` (Information, у ASP.NET Core и EF Core — Warning), меняются без пересборки. В лог не пишутся тела запросов, куки и пароли: журналы входа пишут логин и адрес. **Журнал ошибок** для страницы «Ошибки»: каждое необработанное исключение запроса — в памяти последние 200 (время, метод, путь без строки запроса, логин, тип, сообщение до 1000 и стек до 4000 символов, trace id) и в лог с номером ошибки; клиент получает 500 без подробностей. Сообщение исключения показывается админу как есть (оно может цитировать ввод). В журнал попадают только ошибки HTTP-запросов, включая упавшие команды, которых ждал запрос; сбои планировщика, таймерных команд и хаба (методы хаба тривиальны) — только в логе. Журнал в памяти теряется при перезапуске — полная история в файлах; писать ошибки в базу мимо очереди не стали. Админский `GET /api/admin/errors` (новые сверху; экран — H8). **`/health`** — анонимный, только статусы (`healthy`/`degraded`/`unhealthy`) общий и по проверкам, причины — в логе; 503, если что-то нездорово: база отвечает чтением настоящей таблицы; на диске с базой не меньше `Health:MinFreeDiskMb` (200; на Linux меряется папка базы — примонтированный том, а не корень); очередь команд читается потребителем, ни одна команда не выполняется дольше `Health:MaxCommandSeconds` (60, иначе `unhealthy` — зависшая команда) и ждут не больше `Health:MaxQueuedCommands` (100, иначе `degraded`). Сразу после старта очередь может на мгновение быть `unhealthy`, пока потребитель не запустился: проверка деплоя повторяет запрос. Лимита частоты у `/health` нет: чтение из SQLite дешёвое, ограничение — у прокси (J). Длину очереди считает сама шина: канал с одним читателем не умеет считать элементы. Эндпоинт `/api/test/fail` (исключение нарочно) есть только в окружении Test (A7). **Из ревью безопасности**: неудачный вход пишет в лог существующий логин как есть, а неизвестный — только коротким хэшем (в поле логина может оказаться вставленный пароль, а лог хранится месяц); управляющие символы пути экранируются, чтобы путь не подделал строку лога; исключение пишется в лог один раз (обработчик журнала с номером ошибки, без повтора от middleware); `None` в уровнях выключает категорию. На J: `/health` снаружи отдавать только внутренней сети и проверке деплоя или только общий статус; `var/logs` — на закрытом томе рядом с базой, права только у пользователя приложения. Ловушка генератора OpenAPI (.NET 10): общая схема перечисления строится по первому использованию; если первым встретится поле с `null` (например `EventKind?`), `null` попадёт в само перечисление для всех клиентов. Поэтому новые эндпоинты регистрируются после старых, а сгенерированный клиент сверяется с разницей по `main` глазами.
