# Этап 5 «Ивенты»: разбор разрыва

Подготовка к этапу 5 (2026-11-11, ветка `docs/stage5-plan`). Источники: SPEC «Ивенты», «Взаимодействие игроков», «Голосования», «Челлендж недели», «Доска „ищу напарника“», «Награда за прохождение» (кооп, условия), «Архитектура движка правил», «Модель данных», «Уточнения правил после перепроверки», «Трудности реализации», «Открытые вопросы и проверка на дыры»; CONTENT.md (ивенты 1–5, зона, клетки, голосование, челлендж недели); GLOSSARY; RGG_LEARNINGS (№ 6, 16); код движка `Effects`, `Content`, `Inventory`, `Economy` на `main` 09f21c6 и ветка `feat/items-import` (D-470…D-484) — только чтение. Решения по вопросам, на которые SPEC не отвечает, — D-500…D-529 в `DECISIONS.md`; план — «План этапа 5» в `PROGRESS.md`; строки матрицы — `EV1…EV52` в `TEST_MATRIX.md`.

## Итог в пяти строках

1. **Новых базовых действий не нужно.** Сейчас их 12 из 12 (лимит инварианта 7 выбран полностью; импорт предметов D-470…D-484 добавил только параметры). Всё, что нужно этапу 5 от эффектов, — новые значения и параметры существующих действий: `drawEvent` начинает тянуть из колоды, `requestChoice` получает голосование (`vote`) и отложенный ответ, `modifyNextRoll` — условие прохождения (поле уже есть в формате) и фильтр «конкретная игра», `intercept` — значение `badEvent`, условие — `difficultyAtMost`.
2. **Большая часть этапа — не эффекты, а команды и состояние**: голосования, общие ивенты, кооп, дуэли, доска, челлендж недели, предложка, IRL-пруфы. Они идут той же очередью, как ставки этапа 4, и хранят результаты в событиях.
3. **Ивенты 1, 2, 4 из CONTENT.md играют на нынешнем движке почти без кода**: мешают только стадийные запреты пакета (D-402) и ручной `drawEvent` (D-10). Это и есть тонкий срез.
4. **Две вещи по-настоящему новые в движке**: ожидание ответа посреди эффекта (ивент, вытянутый на чужом толчке, не может спросить «заранее», как предмет, D-407) и эффект на всех от системы (общая цель, итог голосования) под лимитом 50 событий.
5. **Ждут заказчика**: дуэли (правила), кооп (монетки и своё прохождение напарника), откуп от плохого ивента, видео в IRL-пруфе, контракт RGG № 16, Бабл (D-484). У каждого есть дефолт, этап не блокируется.

## 3. Триггеры, селекторы, условия

**Триггеры.** Новых не нужно. Вытягивание — действие, оно срабатывает на уже существующих фазах: остановка (`stop` — клетка ивента; через `CellStops`, как бонус очков), дроп и тех-реролл (встроенные штрафы, D-94), завершение (сложность «выше сложной»), платный реролл. Триггер `time` остаётся отклонённым: общий ивент заканчивается таймером состояния, как лот магазина (D-404), а эффекты общего ивента на часы — объекты со сроком `hours`. Перехват плохого ивента (Бабл, D-484) — проверка при вытягивании с источником «выпало игроку», а не новый триггер: `intercept` получает значение `badEvent` (параметр, как `hostile`).

**Селекторы.** Нынешних хватает: ивент от клетки, дропа, реролла — `self` (вытянувший); голосование — `leader`, `chosen` (варианты-игроки); общий ивент — `all`. Исключения по умолчанию уже в `Targets` (первый финишировавший, неактивные для случайных, финишировавшие не первыми — только очки и монетки, D-424, D-425) и действуют на ивенты без правок. Селекторы импорта (`withinCells`, `nearestBehind`, D-480) тоже работают для ивентов.

**Условия.** `ConditionSpec` уже содержит сложность, фильтр игры и статистики. Нужно: (1) `difficultyAtMost` — «пройди на лёгкой» из SPEC «Противоречащие условия» не выражается без него (параметр условия, D-506); (2) путь проверки условия прохождения при завершении — тот же `Conditions.Hold`, но на снапшоте прохождения, а не на эффекте; (3) условие челленджа недели — тот же тип, проверяется на завершённом прохождении в окне недели. Текстовые условия без автоматики («пройди без смертей») — ручной ивент (`manual: true`), отдельного вида условия не вводим.

## 4. Лимит цепочки (инвариант 8)

| Где | Цепочка | Как держим лимит |
| --- | --- | --- |
| Клетка ивента → ивент толкает → новая клетка ивента | ход → остановка (уровень 1) → ивент с `move` → остановка (уровень 2) → … | ивент разыгрывается внутри обработчика остановки: вытягивание и действия ивента — **один уровень**, а не два (D-500); петля обрывается на 3-м уровне записью `effect-chain-cut`, как петля клеток и предметов этапа 4 (EC10). Приёмочный тест — EV31 |
| Ивент вытягивает ивент (`drawEvent` внутри ивента) | рекурсия через колоду | то же: вложенное вытягивание — следующий уровень; пакет предупреждать не обязан |
| Общий ивент на всех (16 игроков) | запуск → эффект на `all` → по 1–3 события на игрока | 16 × 3 = 48 < 50, но с толчками и клетками не уложится. Решение D-519: в эффектах общего ивента, его награды и итога голосования с целью `all` / `everyone` пакет запрещает `move` и `teleport` (они и по SPEC атаки на позицию — работа предметов); эффекты со сроком выдаются объектом (одно `object-given` на игрока) |
| Итог голосования | закрытие (таймер) → эффект `onResult` | один уровень; на одного (`leader`) — в пределах лимита всегда |
| Награды челленджа недели, дуэли, деление кооп-награды | после команды | **не эффекты**, а расчёты после команды (`Settlements`, D-413): обрыв выплаты был бы порчей данных |

Лимиты остаются константами `Limits` (D-418).

Одна миграция `Events` (имя — по этапу), `Down` снимает только добавленное (проверка отката, `npm run test:migrations` на копии демо-базы). Проверка целостности (D-105) сравнивает новые таблицы с повтором лога.

## 7. Версии событий

Правило: события не переписываются, новые поля — необязательные (D-50), смена смысла — новая версия с преобразованием при чтении (D-49, D-410).

- **Только новые типы**: `event-drawn`, `event-draw-missed` (пустая колода → ручной эффект), `run-condition-attached`, `run-condition-checked`, `irl-proof-submitted`, `irl-proof-reviewed`, `effect-suspended`, `effect-resumed`, `poll-started`, `vote-cast`, `poll-closed`, `poll-cancelled`, `global-event-launched`, `global-progress-changed`, `global-goal-reached`, `global-event-ended`, `interaction-created`, `interaction-answered`, `interaction-expired`, `coop-joined`, `coop-left`, `coop-reward-split`, `duel-settled`, `partner-request-posted`, `partner-request-closed`, `weekly-challenge-set`, `weekly-challenge-completed`, `weekly-challenge-revoked`, `suggestion-submitted`, `suggestion-reviewed`. Имена — план, уточняются в GLOSSARY при реализации.
- **Расширения перечислений без смены формата** (как `ObjectRemoval.ProofRejected`, D-421): `EventKind` + `Special`, `Risky`; `ManualEffectSource` + `Event`, `GlobalEvent`, `Poll`; `ObjectSource` + `Event`, `GlobalEvent`, `Poll`; `ChoiceKind` + `Effect`; `PointsReason`/`MoveReason` + `ConditionUnmet`, `CoopShare`; `CoinsReason` + `WeeklyChallenge`, `Duel`, `GlobalGoal`. Прежний образ не прочитает новое значение — это ожидаемо: откат на прежний образ при включённой новой механике — ситуация «миграция несовместима», бэкап (RUNBOOK); при выключенных флагах новых значений в логе нет.
- **Новые необязательные поля**: `RollModifier.EventKind` (порядок применения, D-505) — пишется только когда есть, снапшоты лога этапа 4 не меняются; снапшот прохождения `RunSnapshot.Conditions`; `RunStarted`/`RunState.PartnerId` не трогаем — напарник приходит отдельным событием `coop-joined`.
- **Кандидат на версию 2**: `manual-effect-created` — если IRL-признак (`proof: media`) положить в него, а не брать из определения объекта. Решение D-509: признак берётся из определения по `ObjectId` (поле уже есть), версия не меняется.
- **Замороженный формат** (`Kernel/EventFormatTests`) пополняется образцами каждого нового типа в той же задаче, где тип появился.

## 8. Очередь команд и «события хранят результаты»

Всё — команды единой очереди (инвариант 2), одна команда — одна транзакция (инвариант 3). Голоса, приглашения, ответы — обычные игровые команды с `commandId` клиента (повтор — дубликат, D-95); сроки — `FireTimers` планировщика (D-404); движок решает по своим часам.

| Механика | Команды | Что событие хранит (результат, а не намерение) | Гонки, которые снимает очередь |
| --- | --- | --- | --- |
| Вытягивание | внутри команды-источника (завершение, дроп, реролл, ход, предмет) | id колоды, **вытянутый объект**, вид ивента, источник; броски ивента — `effect-rolled` | — |
| Ожидание ответа в ивенте | `MakeChoice` (общий, есть) | `effect-suspended`: объект, номер следующего действия, уже вычисленные `$roll`/`$choice`, варианты; `effect-resumed`: ответ | закрытая вкладка ничего не ломает (SPEC «Общий механизм выбора») |
| Голосование | `StartPoll` (админ), `requestChoice.vote` (ивент), `CastVote`, `FireTimers` | снимок вопроса и **вариантов** (выборка игр — уже выбранная), каждый голос, итог с подсчётом и **броском тайбрейка** | два голоса одного пользователя — второй заменяет первый или отклоняется по `polls.allowChangeVote`; голос после срока отклоняется по часам движка даже до таймера |
| Общий ивент | `LaunchGlobalEvent`, `EndGlobalEvent` (админ), `FireTimers` | снимок определения, срок, цель; изменения прогресса — по прохождениям с часами из снапшота | — |
| Кооп | `InviteToCoop`, `AnswerInvitation`, `LeaveCoop`, `FireTimers` | приглашение, ответ, присоединение; при завершении — **деление** суммы броска (`coop-reward-split`: сумма, доли, округление) | приглашающий дропнул, пока напарник принимает, — принятие проверяет состояние в момент выполнения и отказывает `coop.runEnded` |
| Дуэль | `ChallengeToDuel`, `AnswerInvitation`, `FireTimers` | вызов, ответ, итог с победителем и прохождением | два почти одновременных завершения — порядок очереди (как два финиша, SPEC «Проверки на дыры») |
| Доска | `PostPartnerRequest`, `RespondToPartnerRequest`, `ClosePartnerRequest` | запрос, отклик → приглашение | — |
| Челлендж недели | `SetWeeklyChallenge`, `MarkWeeklyChallenge` (ручной), расчёт после `CompleteRun`, `RejectProof` | условие и награда снимком; выполнившие с прохождением | — |
| Предложка | `SubmitSuggestion`, `ReviewSuggestion` | содержимое, решение; одобренная игра — команда пула `AddGame` в той же очереди | — |
| IRL-пруф | `SubmitIrlProof`, `ReviewIrlProof` | файлы, ссылка, решение | — |

**Откат** (инвариант 12): каждая новая команда откатывается целиком снимками затронутых игроков (D-104) и сезонными ключами зависимостей (`poll:{id}`, `interaction:{id}`, `global:{id}`, `challenge:{id}`). Кооп задевает двух игроков и прохождение — ключи `player:a`, `player:b`, `run:x`, откат принятия ждёт откатов более поздних команд обоих. Голос зависит от старта голосования, закрытие — от всех голосов; откат голоса после закрытия отказывает и показывает закрытие.

## 9. Трудности реализации → решения

| Трудность (SPEC) | Где бьёт на этапе 5 | Решение |
| --- | --- | --- |
| Переусложнение движка (≤ 12 действий) | голосования, кооп, общие цели тянут на новые действия | новых действий нет (раздел 1); не-эффектные механики — команды и расчёты (раздел 8) |
| Конструктор эффектов в админке | ивенты и колоды правятся в админке | тот же JSON-редактор со схемой (4.12, ветка `feat/effect-editor`): схема пакета генерируется и включает колоды и ивенты; шаблоны пяти примеров ивентов |
| Ручное применение текстовых | IRL и текстовые ивенты | ручной эффект (D-31, D-102) + пруф (D-509); у игрока прежний ограниченный набор, IRL — только админ |
| Откат действий | кооп на двоих, голосования многих | откат целой команды; зависимости по ключам; закрытие голосования — зависимый от голосов (раздел 8) |
| Таймеры и перезапуск | голосования, приглашения, общие ивенты, челлендж | сроки в состоянии и `Season.NextTimerAt`, `FireTimers` через очередь (D-404); тест перезапуска планировщика |
| Тестирование таймеров | неделя челленджа, 24 ч голосования | `IClock` и перемотка времени (D-120); сценарии тестовой копии: «голосование закрывается через минуту», «на игроке три накопленных ивента», «кооп ждёт ответа» |
| Параллельные записи | голос двух вкладок, принятие и дроп | одна очередь; уникальный индекс голосов — второй рубеж |
| Запросы по JSON-полям | баннер, список голосований, мои приглашения | колонки (раздел 6) |
| Загрузка файлов | IRL-пруфы с фото и видео | фото — существующая загрузка (D-108, D-116), видео — ссылка https без скачивания (D-509): нет SSRF, нет больших файлов на VPS 1 ГБ |
| Расхождение лога и состояния | новые проекции | проверка целостности сравнивает новые таблицы (задача 5.16) |
| Баланс | ивенты двигают очки и позицию | все числа — в конфиге; симулятор этапа 3 получает ботов, тянущих ивенты (задача 5.15, только «ивенты включены/выключены», без кооп и голосований) |
| Объём проекта | этап большой | тонкий срез первым, потом механики по одной за флагом; дуэли и контракт — последними, после ответа заказчика |

Риски сверх таблицы SPEC:

- **Слияние с импортом предметов.** `feat/items-import` меняет `Effects`, `Content`, `ContentPublishing`, `DicePipeline` (D-470…D-484). Задачи движка 5.1+ начинаются после его слияния — иначе конфликты в тех же файлах и двойная работа над `intercept` (Бабл).
- **Скорость главной.** Демо-сезон уже на грани бюджета 2,5 с (D-271). Баннер общего ивента и счётчик приглашений — из колонок, не из повтора лога; замер в задаче 5.21.
- **Анонимность против открытого лога.** SPEC: «лог всех действий виден всем» и «анонимно или нет». Решение D-515 — анонимный голос в ленте без имени; ждёт подтверждения заказчика (в списке вопросов).
- **Ожидание ответа посреди эффекта** — самая рискованная часть движка этапа (повтор лога, откат, лимит цепочки при продолжении). Поэтому она отдельной задачей (5.7) после тонкого среза, а пакет до неё отклоняет ивенты с вопросами (как D-402).
