# Запуск агента

## Подготовка

1. Создай пустой репозиторий на GitHub и склонируй его. Публичный или приватный — см. «Репозиторий и лимиты GitHub» ниже.
2. Скопируй содержимое комплекта в корень репозитория: `CLAUDE.md`, папку `.claude/` и папку `docs/`. Таблицу «Игры крутить» положи в `data/import/games.xlsx`.
3. Проверь, что установлены .NET 10 SDK, Node.js LTS, Docker Desktop, Git и GitHub CLI (`gh`), и выполни `gh auth login`. Через `gh` агент следит за CI и запускает выкладку.
4. Подключи Playwright MCP, чтобы агент мог сам ходить по сайту в браузере: `claude mcp add playwright npx @playwright/mcp@latest`.
5. Запусти Claude Code в папке репозитория. На вопрос, доверяешь ли папке, ответь «да» — иначе хуки из `.claude/` не заработают. Командой `/hooks` можно проверить, что они подхватились.
6. Вставь промпт этапа 1 ниже.

## Репозиторий и лимиты GitHub

- **Публичный репозиторий**: GitHub Actions без лимита минут, можно включить защиту ветки `main` и подтверждение выкладки в настройках окружений. Личных данных в коде нет: таблица с никами лежит в `data/import/` и не попадает в git, секреты — только в GitHub Secrets.
- **Приватный на бесплатном тарифе**: 2000 минут Actions в месяц, защита веток и правила выкладки недоступны. Конвейер всё равно работает: выкладка на боевой сайт — ручной запуск workflow, а «`main` всегда зелёный» держится на дисциплине агента.

## Сервер для выкладки

Нужен к концу этапа 1, на шаге деплоя. Агент подготовит скрипт настройки сервера и попросит тебя:

1. Создать на сервере пользователя для деплоя с доступом только к папке сайта и Docker.
2. Добавить в GitHub Secrets ключ SSH этого пользователя, адрес сервера и отпечаток ключа сервера.
3. Настроить внешнее хранилище для бэкапов и бесплатный мониторинг доступности.

## Как дальше работать

- **Этап 1** начинается с промпта ниже. Агент расскажет, как понял правила, составит план и остановится. Проверь план внимательно: это самое дешёвое место, чтобы поймать неверное понимание.
- **Перед интерфейсом** агент покажет 3 варианта дизайна со скриншотами. Выбери один или опиши словами, что смущает.
- **Следующие этапы**: `/next-phase 2`, `/next-phase 3` и так далее.
- **Каждый день**: `/status` в начале, `/session-end` в конце.
- **Когда хочешь проверку**: `/review` — ревью изменений, `/bughunt` — охота на баги, `/design-review` — ревью интерфейса. Их удобно запускать в новой сессии: свежий взгляд находит больше.
- **Выпуск версии**: `/release` — ревью, PR, CI, автоматическая тестовая копия, затем боевой сайт по твоей команде.
- **Перед сезоном**: бета-сезон на тестовой копии, потом `/preseason` — проверка по чек-листу.
- **Во время сезона**: `/import-bugs` для отчётов с кнопки бага, `/hotfix` для срочных исправлений.
- **Контент**: `/add-content` с описанием предмета, ивента или достижения на русском.
- **Планирование**: для шагов «понимание» и «план» включай режим планирования (Shift+Tab), тогда агент физически не сможет писать код до твоего подтверждения.

## Промпт этапа 1

```
Ты — ведущий разработчик проекта «Игровой ивент»: сайта для дружеского сезонного соревнования по прохождению игр. Я делаю проект один, поэтому ты отвечаешь и за код, и за тесты, и за дизайн, и за эксплуатацию.

В репозитории:
- CLAUDE.md — стек, архитектурные инварианты, команды проекта, инструменты агента и правила работы. Соблюдай их всегда.
- .claude/ — разрешения, хуки, субагенты и навыки. Не меняй без согласования.
- docs/SPEC.md — полная спецификация, источник истины. Только для чтения.
- docs/GLOSSARY.md — названия терминов в интерфейсе и в коде.
- docs/ruleset.default.json и docs/RULESET.md — конфиг правил по умолчанию и описание полей.
- docs/CONTENT.md — формат предметов, эффектов, ивентов и достижений. Реализуется на этапах 4–6, но движок этапа 1 не должен сделать его невозможным.
- docs/TESTING.md — стратегия тестирования, обязательна.
- docs/DESIGN.md — правила дизайна, обязательны. Я не дизайнер, так что за внешний вид и удобство отвечаешь ты.
- data/import/games.xlsx — старая таблица с пулом игр для импорта.

Прочитай CLAUDE.md и все файлы в docs/ полностью, без пропусков.

Сейчас делаем только этап 1 «Фундамент». Цель: на сайте можно провести реальный сезон на простой линейной карте, без предметов, магазина и ивентов.

ШАГ 1 — ПОНИМАНИЕ. Код не пиши. Ответь:
1. Своими словами 10–15 правил предметной области, которые легче всего реализовать неправильно.
2. Как устроишь движок: команды, события, состояние, очередь, IClock, IRandomSource, Ruleset, машина состояний хода, откат.
3. Как устроишь тесты: слои, билдер сценариев, генератор случайных партий и какие инварианты проверишь на этапе 1, как будешь ходить по сайту как пользователь.
4. Как модель эффектов и контента ляжет на docs/CONTENT.md, чтобы этапы 4–6 не потребовали переделки движка.
5. Вопросы, без ответа на которые этап 1 нельзя сделать правильно. Всё остальное реши сам и запиши в docs/DECISIONS.md.

ШАГ 2 — ПЛАН. Составь в docs/PROGRESS.md раздел «Сейчас» и план этапа 1: задачи по порядку, у каждой критерий готовности и тесты, которые её закрывают. Заведи docs/TEST_MATRIX.md с правилами этапа 1. Остановись и дождись моего подтверждения.

ШАГ 3 — РЕАЛИЗАЦИЯ после подтверждения. Порядок:
1. Инструменты проекта: решение и проекты по CLAUDE.md, корневой package.json со всеми командами из таблицы «Команды проекта» (сначала можно заглушками), анализаторы и строгость, архитектурные тесты, husky, lint-staged, gitleaks, .gitignore (включая .claude/state/ и .claude/settings.local.json), .editorconfig, GitHub Actions, Dependabot.
2. Тонкий сквозной срез: ролл → прохождение → кубы → фишка сдвинулась, от базы до экрана, без красоты и без полноты. Всё целиком работает и покрыто тестами.
3. Движок целиком с тестами и инвариантами → инфраструктура и БД → API и SignalR с интеграционными тестами → импорт (чтобы в дизайне были реальные данные) → дизайн → фронтенд с тестами → E2E → эксплуатация и деплой.
Задачи с игровой логикой проходят цепочку субагентов из CLAUDE.md: test-author → реализация → rules-auditor → code-reviewer (и security-reviewer, где нужно) → коммит. После каждой задачи: отметки в PROGRESS.md и TEST_MATRIX.md.

ДИЗАЙН внутри шага 3 — по разделу «Процесс» из docs/DESIGN.md: 3 направления с палитрой, шрифтами с кириллицей и ASCII-макетами → проверка по списку «Чего избегать» → превью главного экрана на реальных данных и скриншоты 390×844 и 1440×900 → остановись и дождись моего выбора → токены и /styleguide → страницы только из компонентов дизайн-системы, каждая проходит design-reviewer.

ШАГ 4 — ОХОТА НА БАГИ И РЕВЬЮ. Выполни то, что делают навыки /bughunt и /design-review: субагенты bug-hunter и design-reviewer на всём этапе, исправления с тестами, пока новые находки не станут мелкими.

ЧТО ВХОДИТ В ЭТАП 1

Движок (библиотека без веба и БД):
- Сезон, игроки сезона, статусы игрока, очки и монетки как поля, прочие ресурсы словарём.
- Ruleset: C#-типы по docs/RULESET.md, конфиг по умолчанию — docs/ruleset.default.json, JSON-схема генерируется из типов. Флаги функций этапов 4–6 выключены, выключенные механики отклоняются движком. История версий конфига.
- Карта — граф; на этапе 1 это цепочка «старт → … → финиш», сгенерированная из конфига.
- Машина состояний хода: Idle, Rolling, Playing, Moving, Resolving, Finished и общий механизм ожидания выбора.
- Ролл: колесо категорий с весами только по категориям с доступными играми; выбор из доступных; промахи («уже прошёл», «сейчас играет») в логе; исключения игрока; кнопка «Уже проходил».
- Реролл по конфигу. Тех-реролл: обязательная причина, окно по конфигу, админ может превратить в дроп. Дроп: кубы за дроп отнимают очки и позицию; обязательный плохой ивент пока создаётся как ручной эффект «разыграть плохой ивент».
- Завершение: сложность, часы обязательны, кубики хранятся по отдельности, очки и позиция растут на сумму, пруф не блокирует, реджект снимает очки и клетки, правка часов докидывает или снимает кубики. «Выше сложной» даёт ручной эффект «хороший ивент».
- Финиш: первый финиш предварительный до одобрения пруфа, заморозка первого, бонус остальным один раз, фиксированная позиция после финиша, пересчёт мест при реджекте финиша, лидерборд и тайбрейки.
- Сезон: статусы (черновик, идёт, закрытие, завершён, архив), после дедлайна броски запрещены, итоги после проверки всех пруфов, снимок итогов при закрытии.
- Лог событий с CommandId, откат команды компенсирующими событиями, проверка целостности пересчётом из лога, экспорт и импорт сезона.

Инфраструктура и веб:
- EF Core + SQLite (WAL), миграции, единая очередь команд с одним потребителем, планировщик по таблице ScheduledTask.
- Аккаунты создаёт админ, вход по логину и паролю, куки, ограничение попыток входа, защита от CSRF. Роли: игрок, админ и зритель (только чтение).
- Файлы на диске: скрины конвертируются в WebP с ограничением разрешения. Аватарки: загрузка или ссылка (только https, только публичные адреса, белый список доменов Tenor, Giphy, Klipy, лимит размера), миниатюры для карты.
- Часы игр через IHoursProvider с ручной реализацией; автоматический клиент HowLongToBeat опционален и не должен ломать сайт.
- Обложки и год выхода через ICoverProvider: Steam (без ключа), IGDB опционально по ключам из переменных окружения, ручная загрузка, аккуратная заглушка. Хранятся на своём сервере.
- Наблюдаемость: Serilog в файл с ротацией, страница «Ошибки» в админке, /health.
- OpenAPI из бэкенда и сгенерированный из него TypeScript-клиент; CI падает, если клиент устарел.
- REST API и SignalR-хаб, который рассылает события сезона.
- Кнопка «Сообщить о баге» с автоматическим контекстом и скриншотом, список отчётов в админке, выгрузка файлом.
- Режим обслуживания: баннер и только чтение.

Фронтенд (React + TypeScript, всё по docs/DESIGN.md, сначала телефон):
- Вход и смена пароля.
- Главная: линейная карта с аватарками, лидерборд (очки и клетки до финиша), текущее прохождение.
- Колесо: анимация готового результата с сервера.
- Страница прохождения: сложность, часы, загрузка пруфа, бросок кубов с анимацией, отзыв, дроп, тех-реролл.
- Лента событий, профиль игрока, страница игры, пул с обложками, поиском, добавлением и предупреждением о похожих названиях.
- Страница правил, собранная из текущего конфига, с историей изменений.
- Админка: игроки и правка их состояния, очередь пруфов (финиши сверху), лог с откатом, пул и категории с весами, конфиг правил как JSON-редактор с валидацией, сезоны, список ручных эффектов, подсказка по неактивным игрокам, отчёты о багах, экспорт и импорт сезона, режим обслуживания.
- В разработке и тестовой копии: загрузка сценариев для ручной проверки и перемотка времени.

Импорт (консольная утилита):
- Из data/import/games.xlsx: лист «Игры» (название, теги через запятую, автор, заметка), лист «Категории» (название, вес). Теги в таблице — формулы, бери вычисленные значения.
- Нормализация названий и тегов, отчёт о дублях и похожих названиях. Авторы сохраняются текстом, чтобы потом привязать к аккаунтам.

Тесты (с первого дня, подробности в docs/TESTING.md):
- Архитектурные тесты и анализатор запрещённых API.
- Сценарные тесты движка через билдер сценариев, снапшот-тесты лога, FsCheck-генератор случайных партий со всеми инвариантами из TESTING.md, применимыми к этапу 1, coverlet, Stryker.NET.
- Тесты конфига и контента, тест миграций на копии демо-базы.
- Интеграционные тесты API, Vitest для фронтенда, Playwright для E2E-сценариев 1–13 из TESTING.md, включая экран телефона.
- Окружение Test: перемотка времени, загрузка сценариев, фиксированное зерно случайности; в Production этих эндпоинтов нет, это проверяет тест.
- data-testid на интерактивных элементах, отключаемые анимации.
- GitHub Actions: быстрые тесты на каждый push, E2E, длинные инварианты и Stryker на pull request и ночью, артефакты с покрытием и трассами Playwright.

Эксплуатация и деплой (по разделу «CI/CD» в docs/SPEC.md):
- Многостадийный Dockerfile, docker-compose для боевого сайта и тестовой копии на одном сервере, Caddyfile, .env.example, скрипт первичной настройки сервера.
- Workflows: ci.yml, nightly.yml, deploy-staging.yml (автоматически после зелёного main, с дымовыми тестами и автооткатом), deploy-prod.yml (ручной запуск, только версия, прошедшая тестовую копию; бэкап, режим обслуживания, миграции отдельным шагом, проверка /health и дымовые тесты только на чтение, автооткат). Образ передаётся по SSH без реестра.
- Дымовые тесты @smoke, работающие против любого адреса.
- Бэкап перед каждой выкладкой, ежедневный бэкап SQLite и файлов во внешнее хранилище, еженедельная проверка восстановления.
- Тег версии и заметки из коммитов для страницы «Что нового».
- Маленький сид для разработки (админ, 5 игроков, 50 игр, сезон) и демо-сезон (16 игроков, весь пул, сотни событий во всех состояниях).
- docs/RUNBOOK.md со всеми пунктами из CLAUDE.md, каждый проверен руками.

ГОТОВНОСТЬ ЭТАПА 1 — всё из раздела «Готовность этапа» в CLAUDE.md. После этого остановись и жди.

Если спецификация противоречит сама себе или CLAUDE.md, не выбирай молча: опиши противоречие и предложи вариант.
```
